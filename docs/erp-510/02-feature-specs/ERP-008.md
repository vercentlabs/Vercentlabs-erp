## Business purpose

Prevent accidental creation of multiple Lead records for the same prospect without collapsing legitimate records or leaking inaccessible CRM data. Duplicate detection is preventive data-integrity logic; it is not Lead Scoring, merging, enrichment, or a bulk-cleanup product.

## Current-code audit before F008 completion

The repository already had several duplicate paths but they disagreed:

- `findCrmDuplicates()` searched active Leads across owners and returned full Lead identity/contact fields.
- Lead Create used that legacy pre-check only as advisory UI; the final create transaction did not enforce it.
- Lead Edit had no contextual duplicate pre-check.
- Lead Acquisition had a separate active-only email/phone query and configurable skip/warn/update behavior.
- CSV import had another bespoke active-only email/phone query.
- public capture could expose Lead IDs/duplicate state in its response.
- migration 064 and `lead-duplicates.js` existed as a partial F008 foundation, but the service was not exported or wired to the canonical mutation paths.
- archived/converted Lead identity was therefore inconsistently considered.

F008 removes these competing enforcement paths by making `lead-duplicates.js` authoritative.

## Canonical matching model

Normalization reuses database-level CRM normalization. Display values are never rewritten merely to compare them.

### Exact / blocking

A Lead is an exact duplicate when any of the following deterministic rules match inside the same organization:

1. same normalized email;
2. same normalized mobile number;
3. same normalized business/alternate phone **and** same normalized full name **and** same normalized company name.

Exact matches are blocked at commit time unless the actor has `crm.data-quality.manage` (or organization-owner authority) and supplies a 10–1000 character reason.

### Probable / warning only

A Lead is a probable duplicate when deterministic combinations such as name + company, business phone + name, or business phone + company match but the evidence is not strong enough for an exact block.

Name-only and company-only similarity never blocks creation.

No F027 Lead Score is used in duplicate classification.

## Scope and privacy

Duplicate **integrity search** is organization-wide and deliberately not owner-scoped. Otherwise Rep B could create a duplicate merely because Rep A owns the original.

Disclosure is evaluated separately:

- a caller who can view the matching Lead receives safe identity metadata (code/name/company/record state and matched signals);
- a caller without record/company/branch/owner visibility receives only `restricted: true`, classification and matched signals;
- contact PII is not returned in F008 match payloads;
- another organization is never searched, blocked, counted or disclosed.

This gives the system stronger integrity without turning duplicate check into an IDOR/enumeration endpoint.

## Database

Migration `064_crm_lead_duplicate_detection_f008.sql`:

- adds canonical comparison-text normalization;
- adds generated normalized mobile, business-phone, name and company columns;
- adds organization-scoped partial indexes for every deterministic lookup path;
- intentionally indexes active, archived and converted Leads so historical identity does not disappear;
- creates forced-RLS immutable `crm_lead_duplicate_overrides` evidence;
- protects override reason length and operation type with database checks.

A broad unique constraint on `(organization_id, normalized_email)` is intentionally **not** used because shared/generic email addresses and historical dirty data can be legitimate. Commit-time serialization instead uses advisory transaction locks keyed to strong normalized identity values.

## Domain/service logic

`lead-duplicates.js` owns:

- normalization;
- strong-identity advisory locks;
- exact/probable classification;
- organization-wide integrity lookup;
- record-safe disclosure;
- override authorization and reason validation;
- immutable override evidence.

`createCrmRecord()` performs F001 validation/source defaults first, then F008 commit-time duplicate enforcement **before F005 assignment policy evaluation**. A rejected duplicate therefore cannot consume round-robin assignment state.

`updateCrmRecord()` evaluates only when an identity field changes, merges the patch with persisted state, excludes the current Lead, and applies the same policy.

Same-record edit is excluded. Unrelated edits do not invoke F008.

## API

`GET /api/crm/leads/duplicates` returns:

- `classification`: none / probable / exact;
- `matches`: disclosure-safe matches;
- `canOverride`;
- temporary `duplicates` alias for compatibility.

Create/PATCH accept `duplicateOverrideReason` only as a governed F008 action parameter; it is kept outside generic CRM field mapping and is never persisted as a Lead field.

F008 errors use actionable codes including:

- `CRM_LEAD_DUPLICATE_EXACT`
- `CRM_LEAD_DUPLICATE_OVERRIDE_FORBIDDEN`
- `CRM_LEAD_DUPLICATE_OVERRIDE_REASON_REQUIRED`

## UI / HCI

Lead Create performs a debounced pre-check using first/last name, company, email, mobile and alternate phone. The user sees **Matching Lead found** for exact matches and **Possible duplicate** for probable matches, with explicit matched signals.

Restricted records show a generic restricted card with no ID, link, contact data or owner information. Authorized exact override displays a bounded reason field and records immutable evidence. The server remains authoritative if the pre-check is stale or unavailable.

Lead Edit performs the same self-excluding check and disables an unresolved exact save. Lead Detail renders restricted matches without Open/Merge actions. F008 does not add a Duplicate Center or new primary navigation.

## Public capture / acquisition / import / offline

- public capture suppresses exact repeat submissions and returns the same generic accepted response whether a record was created or matched;
- public responses never expose Lead ID, owner, lifecycle, qualification or duplicate existence;
- Lead Acquisition delegates duplicate identity to F008 instead of its former bespoke query;
- CSV import delegates to canonical `createCrmRecord()` and counts exact duplicate conflicts as skipped;
- offline sync already delegates Lead creation to `createCrmRecord()`, so it inherits F008 commit-time enforcement;
- F008 does not implement F021 import UX, F029 bulk cleanup, or automatic merge.

## Audit / outbox

Ordinary duplicate pre-checks do not create audit/outbox noise. An authorized exact-duplicate override creates one immutable tenant evidence row containing the new Lead, matched Lead IDs, actor, operation and reason. Rejected checks and ordinary warnings emit no F008 outbox event.

## Concurrency

Strong normalized identity keys are locked with deterministic transaction-scoped advisory locks. Concurrent exact-email/mobile/triple-identity creates serialize; the later transaction rechecks after the earlier commit and receives the exact-duplicate conflict. No global table lock is used.

## Accessibility and responsive behavior

Duplicate feedback is textual, not color-only; links are only rendered when an ID is authorized for disclosure; override textareas have visible focus; create/edit warning surfaces remain within existing responsive Lead layouts, including narrow-phone rules. Server errors remain available even when the advisory pre-check cannot run.
