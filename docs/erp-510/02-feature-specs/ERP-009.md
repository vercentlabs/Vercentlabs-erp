# ERP-009 — CRM Opportunities

## Status

- Feature ID: F009
- Module: CRM
- Feature: Opportunities
- Priority: P0
- Status: TESTING
- UAT: NOT_READY
- Dependencies: protected core foundation and F001–F008

F009 is technically implemented only when the core Opportunity record lifecycle is usable and governed. Named-human UAT is still required before COMPLETE / READY.

## Business purpose

An Opportunity is the canonical CRM record for a qualified revenue pursuit. F009 lets an authorized seller create, find, open, edit, own, relate and archive that record while preserving tenant/company/branch scope, customer context and auditability.

## Scope boundary

F009 deliberately does **not** claim completion of adjacent register items already present in legacy code:

- F010 Opportunity Pipeline — not claimed;
- F011 Probability and Expected Revenue — not claimed;
- F012 Sales Stages — not claimed;
- F022 Lead-to-Opportunity Conversion — existing integration is regression-protected but not claimed here;
- F023 Opportunity-to-Quotation Conversion — existing quotation link/integration is not claimed here.

Pipeline/stage/probability fields remain technically necessary to persist an Opportunity, but F009 only guarantees their initial coherence and prevents generic CRUD bypass. Later features own their richer workflows.

## Pre-implementation audit

The repository already contained `tenant.crm_opportunities`, generic CRM CRUD, an Opportunity detail page, stage movement, reporting and revenue-intelligence code. The core record lifecycle was still incomplete because generic create/update could accept incoherent relationships and lifecycle fields:

- pipeline and stage were independently organization-valid but did not have to belong together;
- arbitrary Lead/Account/Contact IDs were not validated as a coherent accessible customer context;
- owner validation required only active organization membership instead of CRM + company/branch eligibility;
- generic creation could inject terminal status/outcome fields;
- generic PATCH could directly change close/outcome fields outside the governed stage action;
- archived Opportunities remained editable;
- repeated archive emitted repeated events;
- Opportunity audit/outbox payloads were broader than necessary;
- no F009-specific tests, migration, live verifier or UAT matrix existed.

F009 hardens the existing canonical table and generic CRM transport rather than creating a second Opportunity subsystem.

## Canonical record rules

### Create

- Opportunity name is required, trimmed and nonblank.
- New Opportunities always begin `open`. Terminal status, actual close date and outcome fields cannot be injected through generic create.
- Blank owner defaults to the authenticated actor; an explicitly selected owner must be an active CRM-eligible member for the selected company/branch.
- Pipeline/stage are resolved against active configuration. A supplied Stage determines its Pipeline; a supplied Pipeline without Stage uses its first active Stage; blank configuration uses the best active/default Pipeline for the selected company.
- Probability and forecast category are derived from the resolved Stage on create. F009 does not make them user-governed forecast inputs.
- Account must be active. Contact must be active and belong to the selected Account; when Contact is supplied without Account, its Account is derived.
- A linked Lead must be visible to the actor, not archived, and company/branch compatible.
- amount, currency and expected-close inputs are validated so generic/API writes cannot exceed database semantics.

### Update

- Archived Opportunities are read-only.
- Name and ordinary descriptive/customer fields remain editable through the canonical PATCH route.
- Pipeline, Stage, probability, forecast category, status, actual close and won/lost outcome fields cannot be changed through generic PATCH; governed actions own those transitions.
- Account/Contact changes remain coherent.
- Restricted sellers cannot turn a record into a broadly visible unowned Opportunity.
- Selected owners are CRM/company/branch eligible.

### Archive

Archive is a soft transition to `archived`. Replaying archive is idempotent: the existing archived record is returned without another write or outbox event.

## Persistence

Migration `065_crm_opportunities_f009.sql` hardens the existing table:

- repairs only legacy-invalid blank names and enforces nonblank names;
- reconciles historical pipeline/stage mismatches to the Stage's authoritative Pipeline;
- adds a validated composite foreign key `(organization_id,pipeline_id,stage_id)` so mismatched Pipeline/Stage pairs cannot persist;
- adds an organization/company/branch/owner/status scope index for common governed record access.

No new Opportunity table is introduced. Existing RLS and organization-composite FKs remain authoritative.

## Authorization and privacy

All web API traffic continues through authenticated CRM module access, resource permissions and tenant transactions. Existing record scope enforces organization/company/branch/owner visibility. F009 additionally validates selected owner eligibility.

Audit and outbox snapshots for Opportunity CRUD intentionally contain stable IDs, scope, owner, status and relation IDs—not free-text description/next-step/custom data.

## UI / HCI

The existing CRM Opportunity list/editor/detail workflow remains the canonical reachable UI. Derived probability and forecast category are no longer rendered as ordinary editable generic form fields. The detail workspace remains the place to understand the current stage and use governed stage actions.

The existing responsive ERP surfaces and generic empty/loading/error states remain in force; F009 adds no desktop-only route or inaccessible API-only workflow.
