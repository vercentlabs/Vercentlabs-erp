# ERP-011 — Probability and Expected Revenue

## Status

- Dependencies: protected core foundation; F009 Opportunities; F010 Opportunity Pipeline

## Business Purpose

Give authorized sellers a governed way to express deal confidence while making expected revenue mathematically reliable everywhere. Expected revenue is always `round(amount × probability / 100, 2)` in the Opportunity currency.

## Current Code Audit

Before F011, Opportunity probability was stored and initialized/reset from the selected pipeline stage. Generic PATCH correctly blocked direct probability mutation. The Opportunity detail page calculated expected revenue only in React and the dashboard/report layer repeated the formula in SQL. The owner forecast report also included closed Opportunity amounts in its pipeline/weighted totals. There was no dedicated probability action, immutable probability history, or canonical persisted expected-revenue value.

## Functional Requirements

1. Probability accepts 0–100 inclusive with at most two decimal places.
2. Generic Opportunity CRUD remains unable to mutate probability; the governed probability action is canonical.
3. Only authorized users with `crm.opportunities.manage` may change probability and all existing tenant/company/branch/record scope remains enforced.
4. Probability changes are allowed only while the Opportunity is open.
5. A real probability change requires the current `updatedAt` and probability expectations; stale/conflicting writes fail without mutation. An exact desired-state retry is a no-op even when the original response was lost and its token is now stale.
6. Repeating the current probability is an idempotent no-op with no duplicate history/outbox event.
7. Expected revenue is database-generated from amount and probability, rounded to two currency decimals. It automatically changes when amount, probability, or stage-derived probability changes.
8. A committed manual change writes immutable probability history and emits `crm.opportunity.probability_changed`; the Web route writes an audit event in the same transaction.
9. A later F010 stage movement remains authoritative for stage-owned probability and therefore adopts the destination stage probability; generated expected revenue follows automatically.
10. Open forecast totals consume canonical expected revenue and exclude Won/Lost/archived rows from open pipeline/weighted totals.
11. Opportunity list/detail expose expected revenue, and detail provides a keyboard-operable probability editor with calculation preview and actionable errors.

## Database

Migration `066_crm_probability_expected_revenue_f011.sql` adds generated `crm_opportunities.expected_revenue` and immutable tenant-RLS `crm_opportunity_probability_history`. No duplicate Opportunity table or forecast subsystem is created.

## API / Service

`updateOpportunityProbability` locks the scoped Opportunity, validates lifecycle/concurrency, treats exact replay as a no-op, updates only probability/actor/version, relies on the generated column for expected revenue, records history and queues the CRM outbox event. `POST /api/crm/opportunities/:id/probability` preserves same-origin, authentication, server permission, billing write gate, tenant transaction, audit and actionable error mapping.

## Reporting

CRM dashboard and pipeline/owner forecast SQL use `expected_revenue` as the canonical weighted value. Open pipeline and weighted totals filter to `status='open'`; Won revenue remains a separate closed-won metric.
