## Purpose, scope, and exclusions

F005 gives CRM managers one governed way to see, select, manually change, and automatically determine the canonical Lead owner. It covers owner visibility, scoped assignee discovery, manual reassignment, fixed and organization-level round-robin rules, deterministic evaluation, fallback, assignment history, transactional outbox events, security, responsive UX, F001/F004 integration, tests, and UAT.

F006 and later features are excluded. F005 does not implement territories, workload balancing, capacity planning, queues, SLAs, routing analytics, notifications, or arbitrary expression execution. Pre-existing territory/workload schema values remain readable legacy data but are neither exposed nor mutated by this feature.

## Current-state audit and canonical architecture

`tenant.crm_leads.owner_user_id` already existed and remains the only ownership field. Existing organization-aware user FK, owner/status indexes, forced tenant RLS, generic CRM scope enforcement, and Lead list/detail/create surfaces were retained. The repository also contained older `crm_assignment_rules` and round-robin state plus newer `crm_lead_assignment_policies`, state, and event tables. F005 standardizes all new Lead assignment behavior on `crm_lead_assignment_policies`, `crm_lead_assignment_state`, and `crm_lead_assignment_events`; the legacy rule route is closed and no duplicate UI engine remains.

The same domain path handles explicit create ownership, automatic create ownership, manual detail reassignment, and guarded generic owner-only PATCH. Bulk owner changes and mixed generic owner/data patches are rejected so assignment cannot bypass eligibility, scope, audit, or outbox behavior.

## Permission and eligibility model

Manual assignment and rule configuration require `crm.leads.manage` plus `crm.records.view_all`; an organization owner is also authorized. All APIs repeat server authorization, same-origin, entitlement, billing-write, and transactional checks. Rendering a button is never the security boundary.

A newly selected owner must have an active user account, active organization membership, at least one active role granting `crm.view` (or organization-owner role), and access to the Lead's company and branch. Active organization-owner/system-administrator role assignments are unrestricted. Search is server-side, organization scoped, deterministic, paginated, and returns names/emails rather than raw UUID entry. Cross-organization, inactive, removed, CRM-ineligible, and out-of-scope users receive a safe scoped error.

An existing owner who later becomes inactive or loses membership is preserved on historical Leads and displayed as inactive. F005 never rewrites those Leads automatically, but that person cannot be selected for a new assignment or an activated rule.

## Manual assignment behavior

Lead Detail shows the current owner or Unassigned. Authorized managers open Change Owner, use a labelled searchable combobox, and submit once. The row is locked, record scope is checked before change, eligibility is re-evaluated in the transaction, `owner_user_id` is updated, and the response returns human identity metadata. Reassigning to the current owner is an idempotent no-op with no duplicate event. Invalid identifiers fail before querying; stale, unauthorized, or cross-tenant requests fail safely.

Ownership immediately changes F001 record-scope visibility: the previous owner loses owner-derived access and the new owner gains it, subject to the existing manager/global/company/branch rules. Assignment never changes source, status, score, contact data, or another Lead field.

## Automatic assignment and precedence

The deliberate precedence is:

1. An explicitly supplied, authorized and eligible owner on Create Lead.
2. The first active eligible canonical assignment policy, ordered by ascending `sequence` then UUID.
3. Unassigned (`owner_user_id = NULL`).

An explicitly blank owner means Unassigned. Omitting the owner enables automatic evaluation. There is no silent creator/default-owner fallback, making fresh-tenant behavior understandable and avoiding assignment to an ineligible user.

F005 policies allow fixed assignment or organization-level round robin. Criteria are a non-executable allowlist of `sourceId`, two-letter `countryCode`, `industry`, and `productInterest`; all supplied criteria must match. Source criteria must reference an active F004 source in the same organization. Unavailable fixed owners and ineligible round-robin members are skipped. If a matching policy has no eligible owner, evaluation continues to the next ordered policy; if none resolves, the Lead remains unassigned.

Round robin retains configured member order, locks one policy state row with `FOR UPDATE`, advances modulo the eligible set, and is safe under concurrent creation. Policy names are organization-unique and serialized with a transaction advisory lock. Activation rechecks every configured user. Deactivation is soft and affects only future assignments. Editing a rule never rewrites existing Leads.

## Database and migration

Migration `061_crm_lead_assignment_f005.sql` hardens the canonical tables in place. It adds immutable allowlisted criteria validation for fixed/round-robin modes, bounded sequence validation, an evaluation index `(organization_id,status,sequence,id)`, an assignment-history owner index, compatible legacy-rule migration without overwriting canonical conflicts, and documentation comments. Existing composite organization FKs, unique organization/name constraint, state FK, audit-event Lead/policy FKs, and forced RLS remain authoritative.

The criteria check intentionally does not reinterpret retained legacy territory/workload criteria. No ownership column, policy table, or event table was duplicated.

## API and integrations

- `GET /api/crm/leads/assignees`: bounded server search for eligible scoped users.
- `POST /api/crm/leads/[id]/assign`: governed manual reassignment.
- `GET|POST /api/crm/leads/assignment-policies`: list and save F005 policies.
- Rule status/archive actions use the same guarded policy domain service.
- Generic Lead PATCH delegates an owner-only request to `assignLeadOwner`; mixed owner/data and bulk-owner mutations are rejected.

F001 Create omits blank owner values to enable automatic routing and persists explicit eligible selection when present. Lead Detail shows human owner identity, inactive state, Change Owner, and assignment history including rule names/reasons. Lists/Kanban continue to use the canonical owner field.

F004 sources are used by exact `sourceId` criteria. Deactivating a source does not alter the existing Lead's source or owner. Public capture validates its configured owner; an ineligible configured owner falls through to the same canonical policy engine and then Unassigned. Assigned public Leads receive the same assignment event/outbox contract.

## Security, audit, outbox, and concurrency

Every query includes the organization ID and forced RLS remains enabled. Lead scope is checked before manual change; assignee eligibility is organization/company/branch scoped. UUID validation, allowlisted criteria, bounded pagination/sequence, non-executable JSON, duplicate-name locking, row locks, and safe error envelopes address IDOR, injection, stale state, and double submission.

Each real owner transition inserts exactly one `crm_lead_assignment_events` row containing old owner, new owner, optional policy, reason, actor, and time. It also inserts exactly one transactional `crm.leads.assigned` outbox event with identifiers and routing metadata only; Lead contact PII is excluded. Same-owner requests emit neither. These records drive the human-readable history on Lead Detail.

## UX, responsive design, and accessibility

Lead Detail uses a compact owner fact and a simple native modal rather than navigating away. The modal has a programmatic title, Current owner context, searchable combobox, help copy, validation/server feedback, disabled pending controls, Cancel, and Assign owner. Escape closes it, focus enters the modal and returns to the trigger. A Strict Mode dialog-lifecycle defect found by runtime testing was corrected so the modal no longer immediately unmounts.

Assignment Rules is a guided configuration workspace under CRM Setup, not a primary-sidebar destination. It exposes priority, allowlisted conditions, strategy, eligible people, status, empty/loading/error feedback, and practical controls without territory/workload concepts. Desktop uses aligned rows; tablet/mobile stack fields and actions. Required 1920×1080 through 320×568 automation reports zero document overflow for Lead Detail and Assignment Rules. Reduced-motion rules and text status avoid animation/color-only meaning.
