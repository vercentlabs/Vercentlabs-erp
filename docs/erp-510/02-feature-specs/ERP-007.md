## Canonical answer

Lead lifecycle is an organization-wide ordered catalogue stored in `tenant.crm_lead_stages`. `crm_leads.status` contains the stable stage code for compatibility and is protected by an organization-scoped foreign key. Mutable labels never rewrite Lead rows. The separate `crm_leads.record_status` owns `active`, `archived` and `converted`; F006 `qualification_state` remains independent. Opportunity `crm_pipeline_stages` is sales-stage infrastructure and is never reused for Leads.

Default active stages are New, Contacted and Working. New is the protected initial stage. Custom stages receive an immutable generated code and deterministic order. Duplicate names are rejected after trim/case normalization. Stages are never hard-deleted: used stages may be deactivated, historical Leads retain their stage, inactive stages cannot receive new moves, and the initial stage cannot be deactivated.

## Transition governance

`transitionLeadStage` is the only application transition service. The explicit `crm_lead_stage_transitions` graph permits adjacent forward/backward moves; configuration rebuilds it deterministically. An inactive current stage may move to the nearest active neighbour. The service applies tenant/company/branch/owner scope, locks the Lead `FOR UPDATE`, enforces optional optimistic time, blocks archived/converted records and inactive targets, and treats same-stage requests as no-ops.

Each real move changes only lifecycle code and update metadata, inserts one immutable `crm_lead_stage_events` row, and emits one PII-minimal `crm.lead.stage_changed` transactional outbox event. The web action records one platform audit event. Rejected/no-op requests emit none. A database trigger rejects direct `crm_leads.status` writes unless the governed service opens its narrow transaction-local guard.

Generic create/update, mobile create/update, bulk update and offline creation reject lifecycle fields. CSV import cannot map lifecycle after F007 and new Leads always resolve the active initial stage server-side. Public/manual capture also uses canonical Lead creation. Archive, conversion, assignment, source, score and qualification never run implicitly during stage movement.

## APIs and permissions

- `GET|POST /api/crm/lead-stages`: view catalogue or create with `crm.settings.manage`.
- `GET|PATCH /api/crm/lead-stages/[id]`: inspect, rename/reorder, deactivate or reactivate; no DELETE route exists.
- `GET|POST /api/crm/leads/[id]/stage`: history or governed transition with `crm.leads.manage`.
- The legacy `/status` action delegates to `transitionLeadStage`; it is no longer a bypass.

All identifiers are scoped from authenticated context, writes enforce billing and origin controls, and the three F007 tables have forced tenant RLS.

## UX and accessibility

CRM Setup → Lead management → Lead lifecycle provides one responsive catalogue and a right-side create/edit drawer. Stable code, system/initial state, usage, active state and actions remain aligned without adding a permanent secondary navigation level. The drawer is full-width on narrow screens, uses a native modal backdrop, supports Escape/focus containment, labels every control and honors reduced motion.

Lead list tabs, labels and Kanban columns come from server-backed stage metadata. Drag/drop calls the canonical endpoint and refreshes only after success; failures leave the card in place. Every card retains a native Move Lead select showing only legal targets, providing a keyboard/touch alternative. Inactive historical stages remain labelled and readable. Lead Detail uses the same legal-target selector and merges lifecycle events into its timeline.
