## Business purpose, users, and scope

Lead Sources are the governed organization-wide catalogue answering “Where did this Lead originate?” CRM users may use active sources on F001 Leads; only users with `crm.settings.manage` may configure the catalogue. F004 covers catalogue persistence, create/edit, deactivate/reactivate, ordering, validation, permissions, audit/outbox, F001 selectors/display, historical preservation, public ingestion compatibility, responsive UX, tests, and UAT.

F005–F510 and campaigns, attribution models, UTM dashboards, channel ROI, ad integrations, acquisition analytics, import/export implementation, form builders, and source-performance reporting are excluded.

## Persistence and migration architecture

Migration 059 extends `tenant.crm_lead_sources` in place with optional `description`, integer `sort_order`, `is_system`, and `archived_at`. It adds nonblank/length/order checks, an organization-scoped case-insensitive trimmed-name unique index, and an organization/status/order catalogue index. Existing RLS, PK, organization/code uniqueness, and Lead FK remain intact.

If pre-existing names collide after trim/case normalization, the first row remains unchanged and later rows are retained with their stable code appended to the display name. IDs and Lead references are never rewritten or deleted.

`source_id` remains nullable. A Lead may legitimately have “Not specified”; no fake Unknown source is created.

## Default and system-source decision

The repository’s existing eight-source catalogue remains the approved minimal fresh-organization set. F004 does not arbitrarily add Cold Call or integration-specific records. Those eight codes are marked built in, receive deterministic order 10–80, and continue to provision on new organizations. Display metadata may evolve, while code is generated/retained internally and never editable through F004.

## Domain rules

- Name is required, trimmed, nonblank, at most 120 characters, and unique by `lower(btrim(name))` within one organization.
- Description is optional, trimmed, blank-to-null, and at most 500 characters.
- Channel is one of the existing schema channels; sort order is an integer from 0 to 10000.
- New sources start active. Code is generated from the name, normalized, organization-unique, and immutable.
- Status, system flag, archive timestamp, and code are governed fields, not client-editable metadata.
- Deactivate is a soft lifecycle change, clears default state, keeps the row and every FK, and records `archived_at`. Reactivate restores selection eligibility without changing references.
- A new Lead assignment requires an existing active source from the same organization. Cross-organization IDs return scoped not-found behavior and are also blocked by the composite FK.
- An omitted source remains untouched. An explicitly unchanged inactive source may remain during an unrelated Lead edit; another inactive source cannot be newly assigned.
- Public/acquisition ingestion resolves its configured active source. If configuration points to a missing/inactive source, it falls back to the active default, then active Website, then the first ordered active source, or null. This keeps public capture usable and preserves optionality.

## Domain service and API

Business logic lives in `lead-source-operations.js` and the Lead Source validation contract. Operations list, read, create, update, deactivate/reactivate, validate Lead assignment, and resolve ingestion fallback.

- `GET /api/crm/lead-sources`: active/inactive/all, search, bounded pagination; requires `crm.view`.
- `POST /api/crm/lead-sources`: create; requires `crm.settings.manage`.
- `GET /api/crm/lead-sources/[id]`: scoped detail; requires `crm.view`.
- `PATCH /api/crm/lead-sources/[id]`: metadata update or governed reactivation; requires `crm.settings.manage`.
- `DELETE /api/crm/lead-sources/[id]`: semantic deactivate, never hard delete; requires `crm.settings.manage`.

Writes also require same-origin validation, billing write access, usage accounting, module entitlement, and a tenant transaction. The obsolete generic source mutation endpoints return `CRM_LEAD_SOURCE_API_MOVED`. Errors use the established CRM envelope and never expose SQL, constraints, stack traces, or tenant existence.

## Permissions, tenant, and company scope

`crm.view` permits active-source retrieval/use in F001. `crm.settings.manage` separately permits catalogue configuration. Organization-owner behavior remains inherited from core authorization. Explicit `organization_id` predicates plus forced RLS isolate all reads/writes. Lead Sources are organization-wide; no company or branch fields were invented.

## F001 and public-capture integration

Create Lead and source filtering continue to receive active sources only. Edit adds only the Lead’s current inactive source, labelled Inactive, alongside active alternatives. List/Kanban/detail resolve against `allSources`; detail renders the display name plus a text Inactive badge rather than a UUID or blank. Source remains optional.

Single create/update, bulk update, generic public capture, import/acquisition creation, capture forms, and webhooks now use shared server-side source governance. Landing `landing-book-demo` provenance remains unchanged; it does not become a mutable display-name dependency.

## Configuration UX and HCI

CRM Setup → Lead management → Lead Sources remains the only navigation hierarchy. The dedicated workspace provides server search, Active/Inactive/All filters, pagination, usage count for safe confirmation, status text, explicit Deactivate/Reactivate actions, loading/error/empty states, and a right-side focus-trapped create/edit drawer. The form exposes only name, description, channel, display order, and default state; stable code is read-only context on edit.

Desktop uses a compact seven-column configuration table. Tablet replaces it with two-column cards. Mobile uses one-column cards, stacked filters, full-width primary action, sticky form actions, and practical 44px lifecycle targets. Semantic labels, associated field errors, live notices, keyboard-operable controls, focus trapping/restoration, text status, clear confirmation copy, and reduced-motion rules support accessibility.

The Sales seller-dashboard workflow influenced the emphasis on low-friction operational recognition and action safety; no dashboard or analytics artifact was added because F004 is configuration, not source reporting.

## Audit and outbox

Routes record `crm.lead_sources.created`, `.updated`, `.deactivated`, and `.reactivated` audit events in the mutation transaction. Domain operations queue matching transactional outbox events. Metadata contains source ID, stable code/name, status/changed fields, and usage count where relevant; no Lead PII is copied.
