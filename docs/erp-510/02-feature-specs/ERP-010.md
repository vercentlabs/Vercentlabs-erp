# ERP-010 — Opportunity Pipeline

## Status

- Feature ID: F010
- Module: CRM
- Feature: Opportunity Pipeline
- Priority: P0
- Status: TESTING
- UAT: NOT_READY
- Dependencies: protected core foundation; F009 Opportunities; existing CRM pipeline/stage and outcome-reason persistence

## Business Purpose

Give sales users one reliable place to see open Opportunities by stage and move them through the selected pipeline without bypassing tenant/company/branch/record scope, lifecycle rules, concurrency, history, audit or downstream CRM events.

## Existing Code Audit

Before F010, Vercentlabs already had `crm_pipelines`, `crm_pipeline_stages`, Opportunity `pipeline_id`/`stage_id`, stage history, the governed `moveOpportunityStage` service and the authenticated stage API. The board UI, however, passed every visible pipeline and stage into one Kanban, did not choose one pipeline, did not submit stale-write expectations, and could not complete a Won/Lost drop because the backend correctly requires an outcome reason. The Opportunity detail stage action also exposed stages from other pipelines and did not submit the record version.

F010 completes those gaps over the canonical implementation instead of creating a second Opportunity or pipeline subsystem.

## Functional Requirements

1. The pipeline screen selects exactly one active pipeline from the caller's visible company scope; the configured/default-first order remains authoritative when no URL selection is supplied.
2. Only open Opportunities in that pipeline and the caller's existing organization/company/branch/record scope are loaded.
3. Stages displayed on the board belong only to the selected pipeline and follow configured sequence.
4. Authorized users can move an Opportunity by drag/drop or an accessible stage select; read-only users cannot mutate.
5. Every UI transition sends `expectedUpdatedAt` and `expectedStageId` so stale writes or already-moved cards fail safely.
6. A same-stage replay is a mutation-free service no-op.
7. A destination stage must be active and belong to the Opportunity's current pipeline.
8. Won/Lost terminal moves require a compatible active outcome reason and may include notes.
9. Once an Opportunity is no longer open, F010 does not silently reopen it through the stage endpoint.
10. A successful move atomically synchronizes stage-owned status/probability/forecast fields, writes stage history, runs existing CRM automation and emits the existing outbox event. The web route writes its audit event in the same tenant transaction.
11. Empty pipeline, empty stage, error/conflict, no-outcome-reason, large-result warning, keyboard and responsive states remain usable.

## Database

No F010 schema migration is required. Existing persistence is already canonical:

- `tenant.crm_pipelines` owns pipeline identity and company/default scope.
- `tenant.crm_pipeline_stages` owns ordered stages and terminal flags.
- `tenant.crm_opportunities` stores `pipeline_id` and `stage_id`.
- `tenant.crm_opportunity_stage_history` stores immutable movement evidence.
- migration `065_crm_opportunities_f009.sql` already enforces `(organization_id,pipeline_id,stage_id)` coherence with a validated composite foreign key.

Applied migrations remain immutable; F010 does not add redundant tables or columns.

## Domain / Service Logic

`moveOpportunityStage` remains the sole canonical mutation. It locks the scoped Opportunity, checks optional stale-write expectations, treats same-stage replay as a no-op, blocks movement of non-open records, validates the destination against the current pipeline, requires compatible outcome evidence for terminal stages, updates stage-owned fields, writes history, runs CRM automation and emits `crm.opportunity.stage_changed`.

## API

The existing `POST /api/crm/opportunities/:id/stage` remains canonical. It preserves same-origin protection, authenticated workspace/module access, `crm.opportunities.manage`, billing write access, UUID/body validation, tenant transaction, domain execution, audit and mapped errors. No parallel F010 endpoint is introduced.

The existing approval command `crm.opportunity.stage_change` now accepts and forwards `expectedUpdatedAt` and `expectedStageId`, so an approval cannot overwrite a newer stage change.

## UI / UX

The `/crm/pipeline` page now has a visible pipeline selector, scopes stage options and open records to that pipeline, preserves a table fallback when more than 500 open records exist, and keeps the existing horizontal responsive Kanban. Drag/drop is an enhancement; the per-card native select is the keyboard-operable equivalent.

Terminal drop/select opens a governed close form instead of issuing an invalid request. The form filters reasons by Won/Lost compatibility and blocks confirmation if no compatible reason is configured.

The Opportunity detail stage action is also filtered to its own pipeline and submits the current record version.

## Access Control

F010 reuses the shared CRM context and does not bypass:

- organization isolation / tenant RLS;
- active company and branch scope;
- CRM module entitlement inherited from the protected workspace;
- `crm.view` for page reachability;
- `crm.opportunities.manage` for mutation;
- existing record-level owner visibility;
- same-origin and server-side API authorization.

## Integration and Audit

A committed movement writes `crm_opportunity_stage_history`, runs `opportunity.stage_changed` CRM automation, emits `crm.opportunity.stage_changed` to the CRM outbox, and creates the route audit event. There is no direct Stock, Accounting or external side effect for F010.

## Adjacent Features Not Claimed

F010 uses only the minimum existing stage/probability/outcome infrastructure needed to move a pipeline card. It does **not claim**:

- F011 Probability and Expected Revenue;
- F012 Sales Stages administration and richer stage governance;
- F023 Opportunity-to-Quotation Conversion;
- F024 Pipeline Dashboard;
- F025 Sales Forecast;
- F026 Won / Lost Reasons as a complete configuration/reporting feature.
