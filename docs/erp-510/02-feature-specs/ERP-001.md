## Business Purpose

Provide the canonical CRM lead record that a user can create, find, open, edit and archive safely inside the ERP. A lead must remain reachable, tenant-scoped, permission-governed and auditable throughout its lifecycle.

F001 is deliberately limited to the lead record itself. Separate feature IDs own lead sources (F004), assignment (F005), qualification (F006), stages/statuses (F007), duplicate detection (F008), import/export (F021), conversion (F022), lead scoring (F027), custom fields/tags (F028), bulk actions (F029) and CRM reports (F030). Their existing code is not evidence that F001 absorbs those requirements.

## Current Vercentlabs Code Audit

### Existing UI

- `/crm/leads` provides lead list, search and create access.
- `/crm/leads/[id]` provides the lead detail workspace and actions.
- `lead-create-workspace.tsx`, `leads-workspace.tsx` and `lead-detail-workspace.tsx` provide the guided create, list and detail workflows.
- The previous create workspace hard-required mobile even though email or alternate phone are valid contact methods. F001 removes that inconsistency.
- The previous default collection retained archived Leads in the active queue, Lead Detail had no archive action, country was not exposed end-to-end, and the generic edit serializer could erase omitted fields. F001 corrects each defect.
- The unreferenced `lead-actions.tsx` duplicate action panel was removed; governed conversion/merge services and the integrated Lead Detail actions remain intact for their owning feature IDs.

### Existing API

- `GET/POST /api/crm/leads` uses the generic CRM collection route.
- `GET/PATCH/DELETE /api/crm/leads/:id` uses the generic CRM record route.
- Routes enforce authenticated workspace, CRM module/permission access and billing write access, run in tenant transactions, and audit create/update/archive.

### Existing Service Logic

- `services/api/src/modules/crm/index.js` owns lead mapping, CRUD, record scoping, owner governance, numbering, scoring and outbox events.
- F001 adds a lead-specific pure validation boundary at `features/leads/record-validation.js` so authenticated write paths cannot bypass lead invariants.

### Existing Database

- `tenant.crm_leads` already stores organization, company, branch, code, identity/contact fields, owner, source/campaign references, status, priority/rating, estimated value, score, follow-up data and archival/conversion metadata.
- F001 adds database constraints for nonblank first name and at least one usable contact method.

### Existing Permissions and Isolation

- CRM request context applies organization isolation.
- Company and branch scopes fail closed when the user lacks all-company/all-branch access.
- Lead record scope restricts ordinary users to owned/unowned visible records unless `crm.records.view_all` is present.
- Create/update owner assignment is checked against the requesting user's scope.
- Owner reassignment controls are only rendered for `crm.records.view_all` actors (or the organization owner); the API remains authoritative.

## Required F001 Implementation

### Lead record invariants

1. First name is mandatory and cannot be blank.
2. At least one contact method is mandatory: work email, mobile or alternate phone.
3. Email must be valid and normalized to lowercase when supplied.
4. Text is trimmed; blank optional text becomes `NULL` at the domain boundary.
5. Website must use HTTP or HTTPS when supplied.
6. Estimated value cannot be negative or non-finite.
7. Currency and country codes use normalized three/two-letter shapes.
8. Priority, rating and status values must be supported values.
9. A new lead cannot start in `converted` or `archived` state.
10. PATCH validation evaluates the persisted record merged with the patch, so the last contact method cannot be removed.

### Database integrity

Migration: `database/tenant/migrations/055_f001_lead_record_integrity.sql`

- `crm_leads_first_name_present_check`
- `crm_leads_contact_method_present_check`

The constraints are `NOT VALID`: PostgreSQL enforces them for new or changed rows while legacy rows can be audited separately without blocking deployment.

### Domain and service logic

Implementation: `services/api/src/modules/crm/features/leads/record-validation.js`

- `normalizeLeadRecordInput()` canonicalizes lead input before persistence.
- `validateLeadRecord()` performs create/update business validation.
- `createCrmRecord()` normalizes and validates leads before scoring and insertion.
- `updateCrmRecord()` validates the complete candidate record before persistence.
- Domain failures use the existing `CrmError` contract and stable error codes.

### API

No parallel F001 endpoint is introduced. Leads continue through `/api/crm/leads` and `/api/crm/leads/:id`, preserving the existing authorization, tenant transaction and audit chain.

### UI and UX

- First name remains visibly required.
- Mobile is no longer incorrectly hard-required.
- Creation requires at least one of email, mobile or alternate phone and explains that rule.
- Web validation rejects a create request when all three contact fields are blank.
- Country is available in create, edit and detail, and alternate phone is visible on detail.
- Edit serializes only rendered controls, preserving fields hidden by permission or progressive disclosure.
- Default Lead collection queries exclude `archived`; `status=archived` and scoped direct-ID reads retain historical discovery.
- List and detail archive actions use explicit confirmation copy explaining that history is preserved.
- Existing list, search, detail, edit and archive workspaces remain the single F001 workflow.

### Auditability

The existing CRUD routes emit `crm.leads.created`, `crm.leads.updated` and `crm.leads.archived` within the mutation's tenant transaction.

### Cross-module integration

F001 creates and maintains a lead record. Conversion to opportunity/customer/quotation belongs to F022 and is intentionally not a completion requirement for F001.
