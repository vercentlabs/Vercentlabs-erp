## Purpose, users, and scope

Accounts are organisations that CRM users sell to, service, or maintain a commercial relationship with. CRM viewers can search and read Accounts; users with `parties.manage` can create, edit, and archive them.

F002 contains the Accounts workspace, server-backed search, status/industry/country filters, pagination, create, Account 360 identity detail, edit, soft archive, organization/company scope, audit/outbox lifecycle events, responsive UX, accessible states, and automated coverage.

F003–F030 remain excluded. Contact and Opportunity counts are read-only links only. F002 does not add duplicate/merge workflows, lead or opportunity workflows, activities, notes/files, email history, scoring, ABM, hierarchy management, relationship graphs, customer-success health, enrichment, territories, reports, import/export, or bulk actions.

## Current-state repository audit

### UI and routes found before implementation

- `/crm/accounts` used `BusinessDataManager`, loaded up to 500 parties, then filtered customer/prospect types in JavaScript. Search/pagination operated only on that bounded loaded set.
- `/crm/accounts/[id]` ran raw SQL in the page and emphasized pipeline metrics, Contacts, Opportunities, and a combined activity/communication/note timeline. Core edit/archive were missing.
- `/data-management` is a legitimate cross-module party master-data surface and remains.
- Navigation already contained `CRM → Relationships → Accounts` guarded by `crm.view`.
- Native mobile has Leads plus generic business-data APIs but no dedicated Account screen. F002 supplies mobile UX through the canonical responsive web route rather than inventing a parallel native implementation.

### API, service, and obsolete enterprise features

- Generic `/api/business-data/parties` CRUD existed with `business_data.parties.*` audits and `parties.manage` writes.
- No base `/api/crm/accounts` collection/detail lifecycle existed.
- Advanced account hierarchy, merge, duplicates, customer-360, and service-event endpoints existed. `account-intelligence.js` and older account-plan, signal, stakeholder, hierarchy, privacy, merge, and customer-success tables are outside F002. They are absent from the canonical UI but retained as compatibility APIs/data because other modules may call them.

### Persistence and relationships

- `tenant.business_parties` is the canonical shared party/company/customer entity: organization ID, nullable company scope, governed code, party type, display/legal identity, tax/commercial data, status, and timestamps.
- `tenant.addresses` is the canonical shared address entity.
- Contacts, Opportunities, communications, converted Leads, and older account extensions reference the party ID.
- Parties/addresses already use forced organization RLS and organization-aware foreign keys.
- No branch or Account owner exists on `business_parties`; F002 does not invent either.

### Security and tests found before implementation

- `crm.view` gates CRM reads/navigation; `parties.manage` is the approved party maintenance permission.
- CRM API context carries module entitlement, active company/branch, resolved permissions, and elevated scope.
- No focused F002 domain/API/web tests or UAT spec existed. `ERP-002.md` and its register entry were placeholders.

## Architecture decision

F002 reuses `tenant.business_parties` and `tenant.addresses`. No `crm_accounts` or parallel company model is introduced. CRM lifecycle rules live in `services/api/src/modules/crm/account-operations.js`; route handlers contain transport/auth/billing/audit orchestration only. Shared master-data remains available to other ERP modules, while `/crm/accounts` uses the dedicated Account contract.

## Database

Migration `057_f002_crm_accounts.sql` adds `industry`, `website`, `phone`, `email`, and `archived_at` to `business_parties`; an HTTP/HTTPS website check; and list, identity-search, and address-location indexes. Existing RLS, company FK, organization-scoped code uniqueness, address model, timestamps, and party types remain. No destructive rewrite occurs.

## Domain rules

- Company name is required, trimmed, and not whitespace-only.
- Optional blanks normalize to `null`; email lowercases; country/currency uppercase.
- Email is syntactically valid; website is absolute HTTP/HTTPS only.
- Account type is prospect, customer, or both. Supplier-only parties are excluded.
- Code comes from the existing `business_party` numbering series; clients cannot choose it.
- New Accounts start active. PATCH cannot change lifecycle status.
- PATCH merges with persisted data and updates only supplied columns.
- Company scope is derived/checked from authenticated context.
- Address uses the shared primary active address. An address line requires city, state, postal code, and country.
- Archive sets inactive/`archived_at`; it never deletes the party or related rows.
- Database uniqueness/FK/check errors map to safe CRM errors without SQL details.

## API

- `GET /api/crm/accounts`: scoped paginated collection/search/filter
- `POST /api/crm/accounts`: governed create
- `GET /api/crm/accounts/[id]`: scoped detail and relationship counts
- `PATCH /api/crm/accounts/[id]`: partial update
- `DELETE /api/crm/accounts/[id]`: soft archive

All endpoints require authentication, CRM module entitlement, `crm.view`, organization context, and company scope. Writes additionally require `parties.manage`, billing write access, same-origin protection, usage accounting, transactional audit, and safe CRM errors.

## Search and filters

SQL search covers Account code, display/legal name, industry, website, phone, email, and active address city/state/country/postal code. Filters support active/archived/all, industry, and country. Organization/company predicates apply before discovery; inaccessible Accounts cannot leak.

## Authorization and security

- Organization: forced RLS plus explicit organization predicates.
- Company: active-company read predicates and server-side write assertions.
- Branch: not applicable; the canonical party model is not branch scoped.
- Owner/record scope: not applicable; no Account owner exists, so no owner control is exposed or claimed.
- IDOR: identifiers are validated; missing/inaccessible records share safe not-found behavior.
- Archive requires `parties.manage` server-side and never hard-deletes.

## Relationship safety and integrations

F002 never deletes a party, so Contact, address, Opportunity, communication, converted-Lead, and legacy extension IDs remain intact. Account Detail reads only Contact/Opportunity counts and links. F001 Lead conversion already creates/reuses `business_parties`, so converted companies appear without a second model.

## Audit and events

Create/update/archive persist `crm.accounts.created`, `crm.accounts.updated`, and `crm.accounts.archived` audit rows using the same transaction client as the write. Matching CRM outbox events are inserted within the Account domain transaction. Payloads contain IDs, scope, or changed-field names rather than secrets.

## UI, responsive design, and accessibility

Desktop uses a concise heading/action row, server search/basic filters, six-column scan table, empty state, and pagination. Create/edit use the established right drawer with grouped fields/sticky actions. Account Detail prioritizes identity, contact channels, address, scope/timestamps, and related links.

Tablet reflows filters, makes detail single-column, and preserves usable drawer fields. Mobile replaces the table with cards prioritizing name/code, industry, location, and status; filters/forms become one column; detail is vertical with no desktop tab strip.

Semantic headings, fieldsets, labels, required/error associations, live error regions, focus-visible, drawer focus trapping, 44px targets, table headers, text status, archive confirmation, and reduced-motion support are present.
