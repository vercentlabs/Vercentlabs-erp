# ERP-012 — Sales Stages

## Status

- Feature ID: F012
- Module: CRM
- Feature: Sales stages
- Priority: P0
- Status: TESTING
- UAT: NOT_READY
- Dependencies: protected core foundation; F009 Opportunities; F010 Opportunity Pipeline; F011 Probability and Expected Revenue

## Business Purpose

Give CRM administrators one safe catalogue for the ordered stages an Opportunity can move through. Stage configuration must be company/pipeline scoped, deterministic, auditable and compatible with F010 stage movement and F011 probability/expected-revenue behavior.

## Current Code Audit

Before F012, `tenant.crm_pipeline_stages` already stored stage identity, sequence, probability, forecast category, Won/Lost flags and active state, and CRM Setup exposed those fields through the generic CRM resource editor. That was not a complete governed workflow:

- the generic stage resource was marked `companyScoped: false`, so direct stage list/get paths did not inherit the owning pipeline's active-company visibility;
- generic create/update/archive could change pipeline, code, sequence, probability, terminal flags and status without Sales-Stage-specific business rules or optimistic concurrency;
- Won and Lost were independent booleans rather than one governed stage type;
- duplicate active terminal stages, unsafe deactivation and in-use type changes were not prevented;
- stage ordering had no concurrency contract or immutable configuration history;
- Opportunity creation could accept/select an active Won/Lost terminal stage as its initial stage;
- no F012-specific API, workspace, migration, tests, live verifier or UAT matrix existed.

F012 hardens the existing stage table. It does not create a second stage subsystem.

## Functional Requirements

1. CRM Setup → Pipeline → Sales stages opens one dedicated responsive stage workspace.
2. The workspace selects one visible pipeline at a time and shows active and inactive stages separately.
3. Pipeline visibility follows the owning `crm_pipelines.company_id`: an active company selector remains a real scope boundary even for elevated users; organization-wide pipelines remain visible.
4. New stages receive a stable generated code and cannot later move to another pipeline.
5. Stage names are trimmed, nonblank, at most 120 characters and unique case-insensitively within their pipeline.
6. Stage type is exactly `open`, `won` or `lost`. Clients cannot independently forge `isWon` / `isLost`.
7. Open-stage probability is 0–100 inclusive with at most two decimal places. Open stages cannot use forecast category `closed`.
8. Won stages are always probability 100, forecast category `closed`, and no stale-after timer. Lost stages are always probability 0, forecast category `closed`, and no stale-after timer.
9. At most one active Won and one active Lost stage may exist per pipeline. The workspace exposes readiness when either terminal stage is absent or duplicated in legacy data.
10. Active ordering is deterministic. Open stages must remain before terminal alternatives. Reordering requires the current `updatedAt` token for every active stage and stale catalogues fail without partial mutation.
11. Once an active pipeline has an Open-stage catalogue, governed deactivation cannot remove its last active Open stage; pipelines with no configured Open stage remain visibly not ready and cannot create Opportunities.
12. A stage with open Opportunities cannot be deactivated because doing so would make those cards disappear from the active F010 board.
13. A stage that has retained Opportunity usage cannot change between Open, Won and Lost, preserving historical lifecycle meaning.
14. Deactivated historical stages remain queryable and may be reactivated when the pipeline is active and terminal uniqueness remains valid.
15. Configuration edits are prospective: changing a stage default never rewrites an existing Opportunity's stored probability. F010 adopts destination-stage defaults on the next real move; F011 remains the governed manual override.
16. New Opportunity creation may use only an active non-terminal stage. A selected terminal stage is rejected and pipeline-default creation chooses the first active Open stage.
17. Generic stage mutation paths on Web, mobile and the shared CRM service are closed with `CRM_SALES_STAGE_API_MOVED`; existing read compatibility remains available for the mobile pipeline and shared option surfaces.
18. Every committed configuration mutation writes immutable tenant-scoped F012 history and a CRM outbox event. Web routes write the corresponding audit event in the same tenant transaction.
19. Same desired-state update/reactivation/deactivation and unchanged order are idempotent no-ops and do not create duplicate evidence.
20. Server-side `crm.settings.manage`, module access, billing write access, same-origin checks and tenant/company scope remain mandatory regardless of UI visibility.

## Database

Migration `067_crm_sales_stages_f012.sql` keeps `tenant.crm_pipeline_stages` canonical, repairs legacy terminal-stage semantics, repairs blank legacy codes/names, adds nonblank/Won/Lost/Open semantic checks and a catalogue index, and creates immutable RLS-protected `tenant.crm_sales_stage_configuration_history`. Follow-up migration `068_crm_sales_stage_active_order_f012.sql` preserves the already-applied 067 checksum while replacing the legacy all-status sequence uniqueness constraint with active-only uniqueness required by retained inactive historical stages.

Applied migrations remain immutable. F012 does not replace or rewrite F009/F010/F011 persistence.

## Service / API

`services/api/src/modules/crm/sales-stage-operations.js` owns listing visible pipelines/stages, create, update, activate/deactivate, reorder and history. It enforces pipeline scope, stable identity, terminal semantics, usage guards, optimistic concurrency and idempotency. Mutating catalogue operations serialize on the owning pipeline row before stage locks so concurrent rename/type/deactivation/reorder decisions cannot violate catalogue invariants. Reorder and normalization use a two-phase collision-safe sequence assignment so swaps cannot violate PostgreSQL uniqueness mid-transaction.

Canonical configuration endpoints:

- `GET|POST /api/crm/sales-stages`
- `GET|PATCH /api/crm/sales-stages/:id`

The collection POST supports create and governed reorder. Record PATCH supports update, deactivate and reactivate. Generic CRM stage writes return 410 and cannot bypass the domain service.

## UI / UX

`/crm/stages` is a dedicated static route that shadows the old generic `/crm/[resource]` page. It provides pipeline selection, readiness counts, active ordered rows, keyboard-operable up/down ordering, Add/Edit drawer, deactivation/reactivation, usage counts, prospective-default guidance and recent immutable configuration history. Responsive layouts cover desktop, tablet and narrow mobile widths with 44px controls and reduced-motion support.

## Integration

- F009 Opportunity creation now refuses terminal initial stages.
- F010 continues to be the only Opportunity stage-transition action. It consumes active same-pipeline destinations and their configured probability/forecast defaults.
- F011 generated expected revenue automatically follows the probability stored by F010; editing a stage default does not retroactively modify an Opportunity.
- Historical stage and Opportunity-stage history rows keep stable stage IDs/codes/labels even when a stage is later inactive.

## Adjacent Features Not Claimed

F012 does **not claim** F024 Pipeline Dashboard, F025 Sales Forecast, F026 Won / Lost Reasons, approvals/playbooks that may gate stage exit, predictive forecasting, quota management or Sales-module quotation/order stages.
