# F013 — Calls

## Status

- Feature ID: F013
- Module: CRM
- Feature: Calls
- Priority: P0
- Status: TESTING
- UAT: NOT_READY
- Dependencies: protected core foundation; F001 Leads; F002 Accounts; F003 Contacts; F009 Opportunities; existing CRM Activities persistence

## Business Purpose

Give sales users one governed way to schedule and log customer Calls without creating a second activity ledger. A Call must retain who owns it, who/what it relates to, inbound/outbound direction, the phone snapshot used at the time, schedule/execution timestamps, duration and a standardized outcome. The workflow must be safe under tenant/company/branch/owner scope, stale browser/mobile retries, offline replay and existing CRM contact restrictions.

F013 is manual/business Call logging. It does not claim a telephony provider, recording, transcription, dialer infrastructure or conversation-intelligence capability.

## Pre-implementation Code Audit

Before F013, `tenant.crm_activities` already supported `activity_type='call'` together with company/branch scope, relation type/id, subject/description, status, priority, assignee, start/due/end/reminder/completion timestamps and a free-text outcome. `/crm/activities` already provided a focused Calls filter and mobile could create a generic Activity. This was useful foundation but not a complete Call workflow:

1. Call-specific direction was absent.
2. The dialled/received phone snapshot was absent.
3. Actual Call start/end and duration were not governed.
4. Completion stored only unstructured outcome text.
5. Generic Activity CRUD could create/change/archive a Call without Call-specific invariants.
6. Generic Activity completion could bypass a Call lifecycle.
7. Server-side legacy offline sync could directly insert/complete Call rows.
8. No immutable Call event ledger existed.
9. No dedicated Web/mobile Call mutation API existed.
10. Account-linked Calls cannot read a phone from `business_parties` because Accounts do not own a phone column; phone resolution must use Contacts.
11. Existing Lead Follow-up can schedule `activityType='call'`, so F013 must bridge that path rather than break it.

## Required F013 Contract

### Persistence

`tenant.crm_activities` remains canonical. Migration `069_crm_calls_f013.sql` adds nullable Call-only metadata so historical pre-F013 Call rows remain readable:

- `call_direction`: inbound / outbound
- `call_phone`: point-in-time phone snapshot
- `call_outcome_code`: connected / no_answer / busy / voicemail / callback_requested / wrong_number / failed
- `call_started_at`
- `call_ended_at`
- `call_duration_seconds`

Database checks ensure Call-only fields cannot be populated on another Activity type, direction/outcome values are bounded, duration is 0–86,400 seconds and actual start cannot exceed actual end.

`tenant.crm_call_events` is the immutable F013 lifecycle ledger. It records scheduled/logged/updated/started/completed/cancelled events, previous/next status, direction, standardized outcome, duration, actor and timestamp. It deliberately excludes phone numbers and free-text notes. UPDATE/DELETE is trigger-blocked and tenant RLS is ENABLED/FORCED.

### Domain service

`services/api/src/modules/crm/call-operations.js` owns:

- `listCrmCalls`
- `getCrmCall`
- `listCrmCallEvents`
- `createCrmCall`
- `updateCrmCall`
- `startCrmCall`
- `completeCrmCall`
- `cancelCrmCall`

Rules:

1. Only `activity_type='call'` rows are handled.
2. Read scope matches CRM company/branch/assignee ownership semantics.
3. Writes require valid active scope and an eligible CRM assignee.
4. Calls may relate to Lead, Opportunity, Account (`party`), Contact, Campaign or be General.
5. Related records are tenant/scope validated; relationship company/branch must agree with Call scope.
6. Lead phone resolves from mobile/phone.
7. Contact phone resolves from the active Contact.
8. Account phone resolves from its active primary Contact; no nonexistent Account phone column is queried.
9. Opportunity phone resolves from its direct Contact, then active Account Contact.
10. Campaign/General Calls require an explicit phone snapshot.
11. Outbound Calls against a Lead marked `do_not_contact` are rejected before mutation.
12. Phone syntax and digit count are bounded.
13. Scheduled Calls require due time; reminder cannot be after due; start cannot be after due.
14. Planned/overdue Calls may be edited or started.
15. Started/completed/cancelled Calls are not generic-editable.
16. Completion requires a standardized outcome and computes bounded duration from actual start/end.
17. A completed Call updates Lead contact timestamps or Opportunity `last_activity_at` only on real completion/logging.
18. Desired-state start/complete/cancel replays are mutation-free where the supplied final state matches.
19. `expectedUpdatedAt` / `expectedStatus` protect stale state-changing writes.
20. Every real mutation creates immutable Call history and a PII-safe CRM outbox event.

### Bypass closure and integration

- Generic Activity create with `activityType=call` returns `CRM_CALL_API_MOVED`.
- Generic Activity PATCH cannot turn a non-Call Activity into a Call or mutate an existing Call.
- Generic Activity archive cannot archive a Call.
- Generic Activity completion cannot complete a Call.
- Legacy server offline-sync direct Activity insertion/completion rejects Calls and directs modern mobile clients to governed Call endpoints.
- Lead Follow-up with type Call is bridged to `createCrmCall` with outbound direction, Lead phone resolution and do-not-contact enforcement.
- Generic Activity reads remain intact so existing dashboard/search/timeline/reporting surfaces continue to see Call rows.

### Web API

Canonical Web endpoints:

- `GET|POST /api/crm/calls`
- `GET|PATCH /api/crm/calls/:id`
- `POST /api/crm/calls/:id/start`
- `POST /api/crm/calls/:id/complete`
- `POST /api/crm/calls/:id/cancel`

Writes retain same-origin checks, `crm.activities.manage`, billing write checks, usage metering, tenant transaction boundaries and PII-safe audit snapshots.

### Web UX

Calls remain inside the existing focused Activity workspace at `/crm/activities?activityType=call`. F013 does not create a competing activity navigation model.

The Calls view provides:

- server-backed search, status, direction and due filters;
- pagination;
- Schedule Call and Log completed Call;
- CRM relation selectors using real server options, not raw UUID-only input;
- inbound/outbound direction and phone snapshot;
- assignee/priority/schedule/reminder/notes;
- Dial action via `tel:`;
- Edit while planned/overdue;
- Start, Complete with standardized outcome and Cancel;
- immutable Call history drawer;
- responsive/mobile layout, 44px controls and reduced-motion support.

The UI explicitly states that F013 is manual Call logging and does not imply telephony/recording.

### Mobile

The shared mobile SDK exposes create/start/complete/cancel Call methods. Mobile endpoints use the existing durable `withMobileIdempotency` mechanism. Native CRM creation detects `activityType=call` and routes to the governed endpoint. Call create/start/complete/cancel can be queued offline using the existing mutation queue and replayed with the same idempotency key.

## Security and Privacy

- Server authorization is authoritative; UI visibility is not authorization.
- Call reads/writes remain organization/company/branch/owner scoped.
- Related records and assignees are revalidated server-side.
- Outbound Lead do-not-contact is enforced server-side.
- `call_phone`, descriptions and outcome notes are customer PII/content and are not copied into audit/outbox/immutable event payloads.
- The phone snapshot remains on the scoped CRM activity where authorized users need it to execute/history the Call.

## Adjacent Features Not Claimed

F013 does **not claim** F014 Meetings, F015 Tasks, F016 Follow-ups and reminders, F017 Notes and attachments, F018 Email history, F019 Activity timeline, telephony-provider integration, recordings, transcripts, conversation intelligence, automated dialling, call queues, IVR or carrier billing.
