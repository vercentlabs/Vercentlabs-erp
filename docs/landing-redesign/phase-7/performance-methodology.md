# Phase 7 Performance Methodology

This document explains how every performance number in this phase's docs was produced, and — just as important — what each number does and does not mean. It exists because lab and field performance measurement answer different questions, and conflating them produces false confidence.

## Lab vs. field: the core distinction

**Lab data** (what this phase measures) is a synthetic, single-run simulation: one headless Chrome instance, on one machine, loading one page one time, optionally under artificial network/CPU throttling. It is reproducible and useful for diagnosing *why* a page is slow (which resource blocks rendering, which script blocks the main thread), but it is not a measurement of what real visitors experience. A single lab run can vary run-to-run due to local machine load, disk cache state, and background processes.

**Field data** (Core Web Vitals in the strict sense) is an aggregate of real user measurements — actual visitors, actual devices, actual networks, actual connection quality — collected over time and typically summarized at the 75th percentile. Google's CrUX (Chrome User Experience Report) and any real-user-monitoring (RUM) pipeline both produce field data. Field data reflects reality; lab data reflects a controlled simulation of a slice of it.

**This phase has field infrastructure (`lib/web-vitals.ts`, wired into `track()`) but no field data.** The site has not been deployed to production and has received no real visitor traffic, so there is nothing yet for CrUX to aggregate and nothing yet in any analytics backend for the RUM collector to have sent. Every score in `baseline-measurements.md` and `core-web-vitals-audit.md` is lab data. Any statement in this phase's docs about "Core Web Vitals" refers to the field targets (LCP ≤2.5s, INP ≤200ms, CLS ≤0.1 at the 75th percentile) as a goalpost that lab measurements are compared against — never as a claim that field data confirms the site meets them. Where a doc needs to say this explicitly, the exact wording is: *"Field Core Web Vitals are not yet available because sufficient production traffic data is unavailable."*

## What produced the lab numbers in this phase

- **Tool:** Lighthouse (real npm package, `lighthouse@13.4.1`, invoked via its programmatic Node API — see `docs/landing-redesign/phase-7/decision-log.md` item 5 for why the CLI-via-`npx` path was abandoned after three failed attempts specific to this Windows environment).
- **Target:** the real production build — `next build` followed by `scripts/prepare-standalone.mjs`, then `node .next/standalone/apps/landing/server.js`. Never `next dev`, which ships unminified code, disables production optimizations, and would produce meaningless performance numbers.
- **Routes:** the 11 representative routes named in the governing Phase 7 brief (`/`, `/book-demo`, `/product`, `/modules/manufacturing`, `/industries/manufacturing`, `/workflows/lead-to-cash`, `/implementation`, `/resources`, `/resources/erp-buying-guide`, `/resources/erp-requirements-checklist`, `/compare/vercentlabs-vs-odoo`).
- **Form factors:** both `mobile` (Lighthouse's default emulated moderate-throttled mobile profile) and `desktop` (Lighthouse's desktop preset — no throttling beyond a light network/CPU profile matching a typical broadband desktop). These are two different simulated conditions, not two samples of the same condition — mobile scores are consistently lower because the profile is deliberately harsher (simulated mid-tier device CPU + slower network), matching how mobile users actually experience the site more often than not.
- **Categories scored:** Performance, Accessibility, Best Practices, SEO (Lighthouse's four built-in categories, `--only-categories=performance,accessibility,best-practices,seo` equivalent).
- **Single run per route/form-factor combination**, not a median-of-N. This is a real limitation: a single Lighthouse run can vary by a few points between runs due to local machine variance. The baseline numbers should be read as directionally accurate, not exact to the point. Where a later cycle's number differs from an earlier cycle's by only 1-3 points on Performance, that is within expected single-run noise, not necessarily a real regression or improvement — the before/after comparisons in this phase treat only differences of roughly 5+ points, or a change in LCP/CLS/TBT large enough to plausibly explain, as a real signal.
- **Script:** `apps/landing/scripts/lighthouse-baseline.mjs`, committed to the repo. Every score in `baseline-measurements.md` traces to a `summary.json` file this script wrote under `test-results/lighthouse/<label>/` (gitignored — raw reports are reproducible from the script, not committed as artifacts).

## Lighthouse's own scope limits

- **Lighthouse's Accessibility score is not a complete accessibility audit.** It runs a subset of axe-core's automated rules and cannot detect most WCAG failures that require human judgment (meaningful alt text vs. merely present alt text, logical reading order, keyboard-operable custom widgets, correct ARIA semantics for a given interaction, color contrast in dynamically-rendered states Lighthouse doesn't trigger). This phase's actual accessibility findings come from `tests/e2e/accessibility.spec.ts` (the full `@axe-core/playwright` ruleset, not Lighthouse's subset) plus a manual WCAG 2.2 AA pass — see `accessibility-audit.md` and `wcag-22-matrix.md`. A 100 Lighthouse Accessibility score is evidence of "no automated-detectable violation in Lighthouse's subset," not "WCAG AA compliant."
- **Lighthouse's Performance score is a synthetic weighted composite** of several metrics (a formula that has changed across Lighthouse versions), not a single ground-truth number. This phase reports the individual audits (FCP, LCP, TBT, CLS, Speed Index, TTFB) alongside the composite score specifically so a reader can see what's actually driving a low score rather than trusting an opaque 0-100 number alone.
- **Best Practices and SEO scores** are included because Lighthouse produces them for free in the same run and they occasionally surface a real defect (e.g., a missing `viewport` meta tag), but this phase's actual SEO audit is the existing Phase 4-6 SEO/AEO/GEO architecture work plus `search-technical-regression.md` and `search-console-readiness.md`, not the Lighthouse SEO category score.

## RUM (field) methodology, once traffic exists

`apps/landing/lib/web-vitals.ts` collects LCP, INP, and CLS via the official `web-vitals` npm package and routes them through the existing `track()` analytics abstraction with only privacy-safe dimensions (route *pattern*, e.g. `/modules/[slug]`, never the literal URL with query string; rounded metric value; Google's own `good`/`needs-improvement`/`poor` rating bucket; navigation type). No identifying information is attached. Until a real analytics backend is wired to `window.__vercentlabsAnalyticsSink` (documented in `analytics-event-contract.md`) and the site receives real traffic, this collector fires events into a typed interface with no consumer — which is the intended, honest state for this phase, not a bug to fix now.

## What this methodology explicitly rules out claiming

- No CrUX/field percentile number appears anywhere in this phase's docs, because none was obtained.
- No before/after performance claim in `cro-heuristic-audit.md`, `implementation-summary.md`, or the final completion report treats a single-run Lighthouth score difference under ~5 points as a confirmed change.
- No score in any doc is hand-typed from memory or estimated — every one traces to a saved `summary.json` run.
