# Phase 7 Form Friction Audit

## Starting position

The demo-request form was already deliberately reduced from a longer version during Phase 3, on the documented evidence that mid-market buyers abandon forms with more required fields (`docs/landing-redesign/phase-1/conversion-architecture.md`, `docs/landing-redesign/phase-3/decision-log.md`). The governing brief for this phase is explicit: **do not automatically shorten it further** — re-derive the necessity of every field instead of assuming shorter is always better. This audit does exactly that, field by field, against `lib/demo-form-validation.ts`'s real current shape (12 fields total: 11 data fields + 1 consent checkbox, plus 2 hidden honeypot fields) **plus one additional real field this audit's first pass missed** — a 12-checkbox "modules you're curious about" group in `demo-form.tsx` that isn't part of `DemoFormValues` (it's collected separately as `modulesOfInterest`). Found and added during Cycle 2 review (see `decision-log.md` item 18, which also fixed a real accessibility gap on this same field — a missing programmatic group label).

## Field-by-field audit

| Field | Required? | Sales use | Can infer? | Could ask later? | Mobile cost | Decision |
|---|---|---|---|---|---|---|
| `firstName` | **Yes** | Personalizes the first outreach — a sales rep cannot open a call with "Hi there." | No | No — needed for the very first contact | Low (single short text field) | **Keep required.** |
| `lastName` | No | Useful for CRM record completeness, not blocking for first outreach | No | Yes — sales can ask on the call | Low | **Keep optional.** Already correctly optional. |
| `email` | **Yes** | The primary contact channel and lead-dedup key | No | No | Low, but real friction on mobile keyboards without `type="email"`/`autocomplete="email"` (verified present — see `mobile-conversion-audit.md`) | **Keep required.** |
| `phone` | **Yes** | Sales explicitly wants a phone number to schedule the actual demo call, not just email back and forth | No | No — the whole point of "Book a Demo" is scheduling a call | Low with correct `type`/`inputmode` (verified — see below) | **Keep required.** |
| `companyName` | **Yes** | Qualifies the lead (company size/industry lookup, deal sizing) before the first call | No — company name isn't inferable from an email domain reliably (generic domains, subsidiaries) | No — needed to prep for the call | Low | **Keep required.** |
| `jobTitle` | No | Helps sales gauge buying authority | No | Yes — easy small-talk opener on the call | Low | **Keep optional.** |
| `industry` | No | Lets sales route to the right playbook (manufacturing vs. distribution vs. services) before the call | Weakly inferable from company name/domain but unreliably | Yes | Low (a `<select>`, not free text) | **Keep optional.** A pre-selected default from the referring page's context (e.g., landing from `/industries/manufacturing`) would remove even this small cost — see `cro-hypothesis-backlog.md`. |
| `companySize` | No | Deal-sizing signal for sales prioritization | No | Yes | Low (a `<select>`) | **Keep optional.** |
| `primaryInterest` | No | Lets sales open the call around the buyer's actual interest (CRM vs. manufacturing vs. full platform) instead of a generic pitch | Weakly inferable from the referring module/page but not reliably (a visitor could land on `/modules/crm` while actually caring about the full platform) | Yes | Low (a `<select>`) | **Keep optional.** Same contextual-preselection opportunity as `industry`. |
| `mainChallenge` | No | The single highest-value optional field for sales — free text describing the actual problem lets a rep prep specifically instead of generically | No — this is exactly the kind of nuance that can't be inferred | Yes, but loses the buyer's own framing of their problem if deferred to the call | **Highest mobile cost of any field** — a free-text textarea is the most friction-heavy input type on a mobile keyboard | **Keep optional, keep as-is.** The value (a real qualification signal for sales) justifies the field existing at all despite its mobile cost; making it required would meaningfully hurt completion rate for a field whose entire value depends on genuine, unforced buyer input — a required-but-rushed answer is worse than an optional-but-genuine one. |
| `preferredContactTime` | No | Reduces scheduling back-and-forth | No | Yes | Low (a `<select>`) | **Keep optional.** |
| `consentEmail` (checkbox) | **Yes** | Not a sales-data field — a compliance/consent gate for contacting the lead at all | N/A | No — must be captured at submission time, not retroactively | Low (a single checkbox) | **Keep required.** This is the one "required" field that isn't about lead quality at all; it's a legal/trust prerequisite for using the other fields, so it doesn't trade off against completion rate the same way the others do. |
| `modulesOfInterest` (12-checkbox group, one per module) | No | Directly tells sales which modules to demo first — arguably the single highest-leverage optional field for prepping a genuinely relevant call | Weakly inferable from the referring page (and, since Phase 7 Cycle 2, actually pre-checked when arriving via `?module=`/`?industry=`/`?workflow=`/`?solution=` — see `cro-heuristic-audit.md`) | Yes, but loses the buyer's own explicit multi-module interest if deferred | Highest raw on-screen footprint of any field (12 checkboxes) but each individual interaction is trivial (tap a checkbox, no typing) | **Keep optional.** Found missing from this audit's first pass — a real gap, not a judgment call; corrected during Cycle 2 review (`decision-log.md` item 18), which also fixed a real accessibility defect on this same field (no programmatic group label). |

## Summary: no fields removed, no fields added

Every field passed its own necessity test: the 5 required fields (`firstName`, `email`, `phone`, `companyName`, `consentEmail`) are each either needed for the very first sales contact or a consent prerequisite for using the data at all; the 8 optional fields (7 originally audited + `modulesOfInterest`, added after Cycle 2 review) each have a real, named sales use that justifies asking (not asked "just in case") while remaining skippable because none of them blocks the first outreach. This audit found the Phase 3 reduction was already correctly calibrated, not under- or over-trimmed — with one real gap in this audit's own first-pass completeness (the missing `modulesOfInterest` row), corrected before this document was finalized.

## Mobile behavior (cross-referenced with `mobile-conversion-audit.md`)

- Correct input types confirmed: `email` uses `type="email"`, `phone` uses `type="tel"` with a permissive `PHONE_PATTERN` (accepts `+`, parens, spaces, hyphens — doesn't force a rigid format that would reject valid international numbers).
- `autocomplete` attributes are present on the standard fields (name/email/tel/organization), letting mobile keyboards offer saved-value autofill — the single highest-leverage mobile friction reducer for a form this size, verified via `tests/e2e/mobile-conversion.spec.ts`.
- `industry`/`companySize`/`primaryInterest`/`preferredContactTime` are native `<select>` elements, not custom-styled dropdowns — this means they get the OS's native picker UI on mobile (larger touch targets, no custom-JS scroll/tap bugs), a lower-risk choice than a custom combobox component.
- The one field with a real mobile cost — `mainChallenge`'s free-text textarea — is optional specifically because of this cost (see table above), not despite it.

## What was NOT changed and why

No hypothesis in `cro-hypothesis-backlog.md` proposes removing a currently-optional field — every optional field already earns its place per the table above. The one real opportunity found (contextual pre-selection of `industry`/`primaryInterest` based on the referring page) is recorded as a hypothesis, not applied directly, because it requires passing referrer context into the form in a way that hasn't been built or tested this phase — a scoped, testable idea for later, not a same-phase change.
