# Phase 7 Search Console Readiness

**No real Google Search Console (or Bing Webmaster Tools) account or API connector exists in this environment.** This document is an operational readiness guide for whoever configures Search Console after the site is actually deployed to its real production domain — it is not, and does not claim to be, an analysis of real Search Console data. No indexing status, query data, or coverage report referenced anywhere in this phase's docs was obtained from a real Search Console session.

## Canonical production domain

`https://www.vercentlabs.com` — per `apps/landing/.env.example`'s documented `NEXT_PUBLIC_SITE_URL`. `apps/landing/lib/site.ts`'s `SITE_URL` reads this environment variable at build/runtime (falling back to `http://localhost:3000` when unset, which is why this local build's own sitemap/canonical URLs currently read `localhost:3000` — expected local behavior, not a defect. The real deployment must set `NEXT_PUBLIC_SITE_URL` before its first production build.)

## Sitemap location

`https://www.vercentlabs.com/sitemap.xml` (generated by `app/sitemap.ts`). **Real, observed count from this build: 62 URLs.** Verified via `curl http://localhost:3050/sitemap.xml` against the port-3050 verified-production server this phase used for all measurement (see `decision-log.md` item 8) — not estimated.

Per `robots.ts`, everything is indexable (`allow: "/"`) except two explicit disallows:

| Route (pattern) | Indexable? |

## Key clusters to monitor once real Search Console access exists

Per the Phase 1 SEO/AEO/GEO architecture's search-intent ownership model (`docs/landing-redesign/phase-1/seo-aeo-geo-architecture.md`, `search-intent-map.md`):

1. **Module cluster** (`/modules/*`) — 12 pages, each owning its module's category + feature-intent queries.
2. **Industry cluster** (`/industries/*`) — 4 pages, vertical-specific ERP queries.
3. **Workflow cluster** (`/workflows/*`) — 6 routed pages, cross-module process queries ("lead to cash", "procure to pay", etc.).
4. **Resource/glossary cluster** (`/resources/*`, `/resources/glossary/*`) — the organic-acquisition layer; buying-guide, checklist, and definitional-intent queries.
5. **Comparison cluster** (`/compare/*`) — high-intent, bottom-funnel "X vs Y" queries.

## Initial query groups to monitor (illustrative, not measured — these are the intent categories the IA was built to own, not a keyword-research output)

- Brand queries ("vercentlabs", "vercentlabs erp")
- Category queries ("erp software", "multi company erp", "erp for manufacturing")
- Module-specific queries ("erp crm module", "erp stock management")
- Definitional/glossary queries ("what is erp", "what is mrp", "what is rbac")
- Comparison queries ("vercentlabs vs odoo", "odoo alternative")
- Buying-process queries ("erp requirements checklist", "erp buying guide", "erp implementation checklist")

## Core Web Vitals monitoring (once real traffic exists)

Search Console's own Core Web Vitals report is itself CrUX-backed field data — it will show "Not enough data" for any URL below Google's minimum traffic threshold for a long time after launch, especially for the long tail of module/workflow/glossary pages. This is expected, not a misconfiguration. The `web_vitals_lcp`/`web_vitals_inp`/`web_vitals_cls` RUM events (see `performance-methodology.md`) are this project's own first-party alternative that doesn't depend on reaching Google's traffic threshold, once a real analytics backend is wired to consume them.

## Structured-data monitoring

Search Console's Enhancements reports (or the standalone Rich Results Test) should be run against representative URLs from each cluster after launch: a module page, an industry page, a workflow page, a resource guide, a glossary term, and the comparison page — each uses different JSON-LD types per `docs/landing-redesign/phase-4/structured-data-map.md` (`Organization`/`WebSite` sitewide, `BreadcrumbList` via `Breadcrumbs`, plus page-type-specific schema). No structured-data validation tool was run against a live indexed page this phase (none exists yet) — this is a Phase 8/post-launch action item.

## Indexing workflow (once real access exists)

1. Verify domain ownership (DNS TXT record or HTML file, per Search Console's standard flow) — a Phase 8 deployment task, not a code task.
2. Submit `https://www.vercentlabs.com/sitemap.xml`.
3. Request indexing for the homepage and the 5-6 highest-priority cluster-entry pages (`/product`, `/modules`, `/industries`, `/resources`, `/compare`) to accelerate initial crawl.
4. Monitor the Coverage/Indexing report weekly for the first month, watching specifically for: pages Google chose not to index (a signal of thin/duplicate content the Phase 6 quality bar was meant to prevent), and any accidental indexing of the two disallowed routes (would indicate a `robots.ts`/header regression).

## Monthly review procedure (once real access exists)

1. Check the Coverage report for new "Excluded" or "Error" pages.
2. Check the Core Web Vitals report once URLs clear the minimum-traffic threshold; cross-reference against the RUM `web_vitals_*` events for a second, first-party data point.
3. Check the Performance report's query list against the "key clusters" above — confirm each cluster is actually earning impressions for its intended intent, not cannibalizing another page's queries (the ongoing concern `docs/landing-redesign/phase-6/cannibalisation-review.md` first raised).
4. Spot-check 2-3 structured-data-bearing pages via the Rich Results Test for regressions after any content or template change.
5. Re-verify the sitemap URL count is still growing (or intentionally stable) — a sudden drop would indicate a build/routing regression.
