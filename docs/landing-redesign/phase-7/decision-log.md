# Phase 7 Decision Log

Written incrementally as decisions happen, matching the Phase 4-6 practice. Every finding is tagged with its evidence classification (MEASURED / REPRODUCED / OBSERVED / INFERRED / HYPOTHESIS) per the governing brief's explicit requirement.

## 1. REPRODUCED — Real double-submission bug: rapid double-click sends 2 leads, not 1

**Finding:** Building `tests/e2e/lead-reliability.spec.ts`'s double-click test, the first version used two sequentially-awaited `.click()` calls — which passed, but only because Playwright's actionability wait between the two clicks gave React time to re-render and disable the button, masking the real race. Rewriting the test to dispatch two genuine synchronous `element.click()` calls in the same tick (a real double-click, not an artificially spaced one) **reproduced a real bug**: `demo-form.tsx`'s guard (`if (submitting) return`) checks React state, and React batches `setSubmitting(true)` — so both click handlers can read `submitting === false` before either update commits, and both proceed to POST `/api/book-demo`. Confirmed via `requestCount === 2` against a route-level request counter.
**Decision:** Added a `useRef`-backed `submittingRef` alongside the existing `submitting` state. Ref mutations are synchronous and immediate (unlike state), so the second concurrent call now sees `submittingRef.current === true` and returns immediately. `submitting` state is kept for the UI (disabled button, "Submitting…" label) — the ref is purely the synchronous guard.
**Reason selected:** This is the textbook failure mode "state alone can't prevent a race between concurrent synchronous events" — a ref is the standard, minimal fix, not a rewrite of the component's control flow.
**Risk:** None identified — re-verified via the same test (now passing, `requestCount === 1`) and the full `lead-reliability.spec.ts`/`pii-leakage.spec.ts` suites (9/9 pass) after the fix, plus `typecheck`/`lint` clean.
**Severity:** P0 — a duplicate lead is a real, tangible business cost (sales team following up twice on the same inquiry, or the CRM proxy's own dedup logic, if any, being relied on to paper over a client-side bug that shouldn't exist).

## 3. MEASURED — Site-wide WCAG AA color-contrast failure, found by the first real axe-core run this project has ever had

**Finding:** Running `accessibility.spec.ts` (axe-core, `wcag2a`/`wcag2aa`/`wcag22aa` tags) against all 13 representative routes for the first time found 9 of 13 failing with `color-contrast` (serious impact) — 228 total nodes. Every single failure traced to the same root cause: `--color-text-secondary`/`--color-text-muted` (`#667085`) rendered against `--color-bg-subtle`/`--color-bg-selected`/`--color-brand-soft` (`#eef2ff`) computes to a 4.44:1 contrast ratio — just under WCAG AA's 4.5:1 minimum for normal-size text. This is a real design-token pairing baked into `packages/landing-content/src/tokens.js` (the token system's own documented single source of truth, mirrored into `apps/landing/app/globals.css` and enforced in sync by `tokens-sync.test.mjs`) — not a one-off component bug, which is why it appeared everywhere the "subtle" tone band is used (alternating page sections, the requirements checklist's whole body, the comparison table's zebra striping).
**Decision:** Darkened `COLOR_TOKENS.mutedInk` from `#667085` to `#5d6b81` — computed via the real WCAG relative-luminance formula (not guessed), chosen as the minimal darkening among several candidates that clears 4.5:1 with real margin (4.83:1) rather than just barely passing. Updated at the token source (`tokens.js`), mirrored into `globals.css` per the existing sync convention, and also fixed a third, independent hardcoded copy of the old hex in `app/opengraph-image.tsx` (an Open Graph image generator not covered by axe since it renders to a PNG, not scanned DOM) — replaced with a real import of `COLOR_TOKENS.mutedInk` instead of a 4th hardcoded copy, closing the drift risk permanently.
**Reason selected:** A single-token fix is the minimal, correct intervention for a systemic pairing issue — not a broader redesign (explicitly out of Phase 7 scope), and not a per-component workaround (which would have left the same failure everywhere the token pair is reused).
**Verification:** Full rebuild + fresh server boot + re-ran both the ad hoc axe summary script and the formal `accessibility.spec.ts` suite: **0 serious/critical violations across all 13 routes** (down from 228 nodes/9 routes). `tokens-sync.test.mjs` (3/3), full unit suite (156/156), `typecheck`/`lint` all stayed green.
**Severity:** P0 — a real WCAG AA violation is a real accessibility barrier for low-vision users, present on the vast majority of the site's routes, not a hypothetical or edge-case concern.

## 5. Scope deviation — Lighthouse invocation switched from `npx` CLI subprocess to the programmatic Node API

**Finding:** The plan's scope decision #4 called for an on-demand `npx lighthouse` CLI invocation (no new heavy devDependency). The first two attempts at this both failed for real, reproducible reasons, not flakiness: (1) `execFileSync("npx", args)` throws `ENOENT` on Windows because `npx` resolves to `npx.cmd`, which requires shell resolution; (2) adding `shell: true` "fixed" the ENOENT but silently broke every single run (22/22 failed) because `shell: true` concatenates arguments **without quoting** them (Node's own runtime prints a `DEP0190` warning about exactly this), and this repository's absolute path contains a space (`C:\Project\VERCENTLABS ERP\...`) — the `--output-path` argument was truncated at that space on every run, producing two different-looking downstream errors (`EISDIR` when the truncated path pointed at a real directory, `EPERM` during chrome-launcher cleanup on the runs where it didn't) that were actually one root cause; (3) invoking `npx.cmd` directly without `shell: true` throws `EINVAL` — Windows `execFileSync`/`execFile` cannot spawn `.cmd`/`.bat` files without a shell, a documented Node limitation.
**Decision:** Added `lighthouse` and `chrome-launcher` as real devDependencies and rewrote `scripts/lighthouse-baseline.mjs` to call Lighthouse's programmatic Node API (`import lighthouse from "lighthouse"`) directly against a `chrome-launcher`-managed Chrome instance, with no subprocess/shell/argument-quoting involved at all.
**Reason selected:** Every subprocess-based path to `npx lighthouse` was independently broken in this specific Windows environment (this repo's path containing a space is the actual trigger — a detail worth flagging for any future CI environment too, in case it also uses a path with a space). The programmatic API is the officially documented alternative for exactly this kind of integration and eliminates the whole bug class rather than adding a third workaround on top of two failed ones.
**Verification:** Full 22-run baseline (11 routes × mobile/desktop) completed successfully end-to-end with real scores (see `baseline-measurements.md`) — 0 failures, 0 skipped runs.
**Risk:** None identified for this repo. `lighthouse`/`chrome-launcher` add real install weight to `devDependencies` (not shipped in the production build), which is the one real cost of this deviation from the plan's original "no new heavy devDependency" preference — accepted because the alternative (a subprocess CLI call) does not actually work in this environment.

## 7. Test-authoring bug in the new attribution test suite — hydration race, not a product bug

**Finding:** `tests/e2e/attribution.spec.ts` (new this phase) initially read `localStorage` via `page.evaluate()` immediately after `page.goto()`. `AttributionInit` captures first-touch attribution inside a client-side `useEffect`, which only runs after React hydration completes — on the `mobile-chromium` project (slower emulated profile), 4 of 9 tests raced ahead of hydration and read `null`/stale state. The `desktop-chromium` project passed all 9 on the first attempt, which is what exposed this as a timing race rather than a real cross-browser attribution bug.
**Decision:** Added a `page.waitForFunction()` poll (5s timeout) for the localStorage key to exist before reading it, matching the same category of fix as this phase's other test-authoring bugs (item 4).
**Verification:** All 18/18 (9 scenarios × 2 projects) pass after the fix: initial campaign capture, internal-nav non-overwrite, refresh persistence, back/forward persistence, second-campaign non-overwrite, direct-revisit non-overwrite, no-param direct/referral fallback, oversized-UTM truncation, and availability at demo-form submission time.
**Product finding (informational, not a defect):** `AttributionRecord` has no expiry/TTL — a first-touch record persists in `localStorage` indefinitely until the browser's storage is cleared. This is a deliberate, reasonable choice for a first-touch model within a single browser profile (there's no "session" to expire against), but it is worth stating explicitly since the brief requires expiry behavior to be defined, not left implicit: this implementation's expiry policy is "never, until the visitor clears site data or uses a different browser/device," which produces one edge case worth naming — a visitor who first arrives via a campaign link, doesn't convert, and returns weeks later via organic search will still be attributed to the original campaign. This is standard first-touch-model behavior industry-wide, not a bug, and no change was made.

## 8. MEASURED — A stray external `next dev` process could have silently invalidated production measurements; all measurement re-run against a dedicated, verified port

**Finding:** While investigating unexpectedly noisy/low Lighthouse mobile scores, `netstat -ano` showed port 3000 bound to PID 12256, a child of PID 16304 (`next dev -p 3000`), itself a child of a `pnpm --parallel --filter @vercentlabs/landing --filter @vercentlabs/web dev` process (PID 4680, `CreationDate 2026-08-08 09:10:19`) — a dev-mode process this session never started. Confirmed via response inspection: `curl -D -` against port 3000 showed `Cache-Control: no-cache, must-revalidate` and a CSP containing `'unsafe-eval'` in `script-src` (the dev-only CSP branch), and the HTML referenced unminified, source-path-derived chunk names (e.g. `apps_landing_app_layout_tsx_139x68y._.js`, `next-devtools`) rather than production's short hashed chunk names. `playwright.config.ts`'s `webServer` block uses `reuseExistingServer: !process.env.CI`, which happily reuses *any* server already listening on port 3000 without verifying it's actually the production build — meaning if this external dev process grabbed port 3000 at any point after this session's own standalone server (started via a backgrounded shell subprocess, a fragile pattern on Windows Git Bash) exited, every subsequent Playwright/Lighthouse run against `localhost:3000` would have silently measured dev-mode performance and reported it as a production baseline.
**Decision:** Rather than determine exactly which of this session's already-completed runs were and weren't affected (the dev process's creation timestamp doesn't cleanly bound the uncertainty), every measurement this phase relies on was re-run against a dedicated production server on port 3050 (`PORT=3050 NODE_ENV=production node .next/standalone/apps/landing/server.js`), verified clean via the same response-inspection method (hashed chunk names, `x-nextjs-cache`/`x-nextjs-prerender` headers present, no `'unsafe-eval'` in CSP) before any measurement was trusted. The external dev server on port 3000 was left untouched — it predates this session's own actions and is not this session's process to kill.
**Reason selected:** A silently-contaminated "production baseline" is worse than a slower, fully-reverified one — the whole point of this phase's evidence discipline is that a claimed MEASURED number must actually trace to the real production build, not an assumption that a listening port implies the right build.
**Risk / residual finding:** `playwright.config.ts`'s `reuseExistingServer` + unverified-port pattern is a real, generally-applicable footgun, not unique to this incident — recorded as a `phase-8-brief.md` follow-up (verify the server responding on the target port is actually a production build before trusting any port-reuse in CI or local runs, e.g. by asserting on a response header production sets and dev doesn't).

**Finding:** The clean, retry-protected Lighthouse baseline against port 3050 (22/22 runs, zero runtimeErrors) found 3 routes with an `<img>` element (not text) as the actual LCP element: `/industries/manufacturing` (mobile LCP 3192ms, over the 2.5s field target), `/product` (1696ms), `/workflows/lead-to-cash` (1687ms). ## 11. REPRODUCED — Skip link scrolled but never moved keyboard focus, a real WCAG 2.4.1 gap

**Finding:** A throwaway Playwright script (not committed — used only to verify this specific behavior, then deleted) confirmed `app/layout.tsx`'s skip link (`<a href="#main-content">`) was reachable first via `Tab` and activatable via `Enter`, but afterward `document.activeElement` was neither `#main-content` nor any element with that id — the browser scrolled the viewport to the fragment target but never moved keyboard focus there, because `<main id="main-content">` had no `tabIndex`, and a plain `<main>` element isn't natively focusable. This means a keyboard-only or screen-reader user activating the skip link got a visual scroll but no actual focus jump past the header/nav — defeating the skip link's real purpose (WCAG 2.4.1 Bypass Blocks) despite the link itself existing and being reachable.
**Decision:** Added `tabIndex={-1}` to `<main id="main-content">`, the standard, well-established pattern for a skip-link target (used by e.g. GOV.UK's design system) — this makes the element programmatically focusable without adding it to the normal Tab order (a `-1` tabindex is reachable only via script/fragment-navigation, never via sequential Tab). Paired with `className="focus:outline-none"` on the same element, since drawing a visible focus ring around the entire page-content landmark (rather than a specific control) would look broken, not helpful — this is also standard practice for this exact pattern.
**Reason selected:** The minimal, correct, standard fix for exactly this class of bug — no JavaScript focus-management code needed, since the native `tabindex` + fragment-navigation combination handles it.
**Verification:** Re-ran the same throwaway script after the fix (rebuild + reboot) — `document.activeElement.id` is now `"main-content"` after skip-link activation, confirmed. Full `typecheck`/`lint` clean.
**Severity:** P1 — a real, if narrow, accessibility defect (skip links exist specifically for keyboard/screen-reader users, and this one didn't functionally work for its stated purpose), fixed directly per the brief's own instruction not to experiment with confirmed accessibility defects.

## 13. MEASURED — `null`/non-object JSON body crashed `/api/book-demo` into an uncaught, unlogged 500

**Finding (Cycle 2, lead-reliability review):** `validateDemoForm(body)` (`route.ts`) sat outside any `try/catch`. `JSON.parse("null")` succeeds (valid JSON), so a body of literal `null` reached `validateDemoForm`, which immediately threw on `values.firstName` property access against `null`. REPRODUCED via `curl -X POST --data "null"` — a bare, non-JSON 500 with no `{ok, requestId, error}` shape, and critically, invisible to `lead-observability.ts` (no log call is ever reached).
**Decision:** Added a guard immediately after JSON parsing: `if (!body || typeof body !== "object") return 400`.
**Verification:** `typecheck`/`lint` clean; re-verified post-rebuild (see Cycle 3).
**Severity:** P1 — a real, if narrow (requires a non-browser client sending literal `null`), gap in the "no path crashes unhandled" guarantee.

## 14. MEASURED (cross-repo) — Client-supplied `attribution` object could silently overwrite trusted `requestId`/`source` fields sent to the CRM

**Finding (Cycle 2, lead-reliability review):** `route.ts`'s `customData` spread `...(body.attribution ?? {})` **last**, after `requestId`/`source` — in a JS object literal, a later key wins, so a POST body containing `attribution: {requestId: "x", source: "x"}` would overwrite the server-trusted values before forwarding to the CRM capture endpoint. Confirmed `apps/web`'s `publicCaptureSchema` (`crm-validation.ts`) uses an open `z.record(z.string(), z.unknown())` for `customData`, so nothing downstream would catch this either.
**Decision:** Reordered the spread — `...(body.attribution ?? {})` now comes first, `requestId`/`source` last, so trusted server values always win regardless of client input.
**Reason selected:** Minimal, correct fix — no new validation layer needed, just correct precedence.
**Severity:** P2 — a data-integrity/traceability risk (corrupted lead-source attribution for CRM records), not a PII leak or crash.

## 15. MEASURED — Rate-limiter's in-memory Map had no eviction, unbounded growth risk in a long-running process

**Finding (Cycle 2, lead-reliability review):** `lib/rate-limit.ts`'s `buckets` Map reset expired entries' `count`/`resetAt` in place but never `.delete()`d them — every unique rate-limit key (`book-demo:${ip}`) ever seen is retained forever, an undocumented gap in the file's own limitation comment.
**Decision:** Added lazy pruning (`pruneExpired()`, a full Map sweep removing expired entries) triggered whenever a new/expired key is processed — no background timer needed.
**Severity:** P2/P3 — a real but slow-building risk (weeks/months of unique-IP traffic in a single long-running process without redeploy), not an immediate concern.

## 18. REPRODUCED — Module-interest checkbox group had no programmatic group label (WCAG 1.3.1)

**Finding (Cycle 2, accessibility review):** `demo-form.tsx`'s 12-checkbox "Modules you're curious about" group used a bare `<Text variant="label">` (renders as an unassociated `<span>`), not a `<fieldset>/<legend>` or `role="group"`. A screen-reader user tabbing through would hear only "CRM, checkbox", "Sales, checkbox", etc., with no group context — axe-core doesn't reliably flag this class of issue, which is why it survived the 13/13 clean run.

**Severity:** P2 — a real, moderate accessibility gap in a real form field, fixed directly per the brief's own instruction not to experiment with confirmed accessibility defects.

## 20. REPRODUCED — Genuine intermittent race in a new Phase 7 test (`attribution.spec.ts`), not a product bug

**Finding:** During Cycle 3's full regression run, `"attribution reaches the demo form submission"` failed intermittently (~50% of repeated runs, confirmed via 8+ manual re-runs). Root cause: unlike its sibling tests, this test never waited for the *first* page's `AttributionInit` `useEffect` to actually write to `localStorage` before calling `page.goto("/book-demo")` — `goto()` only waits for the navigation's `load` event, not for a post-paint React effect to run. When the second navigation raced ahead of the first page's own capture, `/book-demo`'s `AttributionInit` (seeing no existing record, and no UTM params in its own URL) captured a *new* first-touch record with `utmSource: undefined` — matching the exact observed symptom.
**Decision:** Added the same `readAttribution(page)` wait on the first page that every passing sibling test already uses (established at the top of the file) — REPRODUCED as fixed via 8/8 consecutive passing runs (previously ~50% failure rate under the identical repeated-run methodology).
**Reason selected:** This is a test-construction bug (a missing synchronization point), not a product defect — manual verification throughout this investigation consistently showed the real app's attribution data is correctly written and persisted; only this one test's timing assumption was wrong.
**Note on process:** An initial fix attempt (`expect(...).toPass()` polling) did not resolve it, because the failure wasn't a slow-to-settle read — it was a genuinely different, wrong value being written by a real race in the test itself. Retrying/polling around the wrong root cause doesn't fix a race at the wrong layer; this is recorded because it's a useful cautionary example for future test debugging in this repo.
