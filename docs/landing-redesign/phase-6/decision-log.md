# Phase 6 Decision Log

This log is written incrementally as decisions happen, not reconstructed at the end — matching the Phase 4/5 practice. Entries are numbered in the order they were made.

## 1. Mobile CTA "gap" was actually a duplication, not an absence — root-caused before touching anything

**Finding:** The Phase 5 UX/CRO reviewer flagged a mobile header CTA gap. Investigation (real Playwright `isVisible()` sweep across 320/375/390/480/600/768/1024px, backed by a real screenshot) found `StickyMobileCta` (`components/marketing/sticky-mobile-cta.tsx`, mounted globally in `app/layout.tsx`) already covers 320–1023px via `lg:hidden`. The real bug was the opposite of what was reported: the header CTA's `hidden sm:block` and the sticky bar's `lg:hidden` together produced a 480–1023px window where **both** were visible simultaneously — confirmed via a 768px screenshot showing 3 "Book a Product Demo" prompts on screen at once.
**Decision:** Aligned `StickyMobileCta`'s breakpoint to `sm:hidden` (matching the header's own `hidden sm:block` exactly) instead of building new mobile-CTA infrastructure. Re-verified with a second Playwright sweep: zero duplicates, zero gaps, 320px–1024px+.
**Reason selected:** The brief's own instruction was "inspect actual screenshots, do not guess" — doing so revealed the prior finding's diagnosis was wrong, and the real fix was a one-line breakpoint alignment, not a new component.
**Risk:** None identified — both breakpoints now derive from the same Tailwind `sm` value; a future edit to one without the other would reintroduce the dead zone, so this is a legitimate visual-regression-test candidate for Phase 7 (screenshot diff at 480px/1023px specifically).

## 2. Sitemap freshness: real per-route dates grounded in git history, not invented

**Finding:** `sitemap.ts` applied one `HOMEPAGE_METADATA.lastReviewed` date to all 52+ routes uniformly — flagged in Phase 4's decision log, reflagged as still-deferred in Phase 5's.
**Decision:** Built `packages/landing-content/src/freshness.js` exporting `CONTENT_FRESHNESS`, keyed by real pathname, with `publishedAt`/`lastModifiedAt`/`lastReviewedAt` derived from `git log --format=%ad -- <file>` against the actual files that back each route, plus a `reviewReason` stating in plain language what the last significant change actually was. `getFreshness()` throws on any route missing an entry, so a new route can't silently regress to a placeholder date. `sitemap.ts` now reads `getFreshness(path).lastModifiedAt` per route.
**Alternatives considered:** Computing dates dynamically at build time from live git log output (rejected — non-deterministic across environments/shallow clones, and the brief explicitly warns against build-time dates); inventing varied-looking dates for visual plausibility (rejected — a direct Evidence and Honesty Rules violation).
**Reason selected:** Hand-derived, hard-coded dates from real commit history are deterministic, auditable, and honest even though this project's actual build history spans only 2026-08-05 through the current date (a compressed real timeline, not weeks) — meaning dates legitimately cluster. The `reviewReason` field carries the real signal even where dates repeat.
**Risk:** Dates must be manually updated when a route's content changes — there is no automated enforcement that `lastModifiedAt` actually reflects the most recent substantive commit. Mitigated partially by `freshness.test.mjs`'s date-ordering and required-route-coverage checks, but not by a check that the date is *current*. Flagged for Phase 7's `content:stale` tooling to build on.

**Reason selected:** The brief explicitly warns against forcing irrelevant screenshots onto pages that lack real evidence; `multi-company-management` keeps its existing "Built into" module-tag fallback (already a deliberate, tested Phase 4 pattern for evidence-light pages) rather than being paired with a screenshot that doesn't show what the page claims.

## 5. Workflow sequence-step overlap: `order-to-fulfilment` trimmed to cross-reference `lead-to-cash` instead of restating it

**Finding:** `order-to-fulfilment`'s sequence carried 2 of its 5 steps ("Order conversion", "Credit check and confirmation") with detail text nearly identical, sentence-for-sentence, to `lead-to-cash`'s "Convert to order" and "Credit check and confirm" steps, and its "Invoice generation" step closely restated `lead-to-cash`'s "Invoice" step. This is the exact residual overlap the brief named as a carried-forward P1 issue, and Phase 5's `directDefinition` framing fix (revenue-team vs. warehouse/finance angle) only addressed the hero-level framing, not the sequence body text itself.
**Decision:** Consolidated `order-to-fulfilment`'s first two steps into one shorter step ("Order confirmed (see Lead to Cash)") that explicitly cross-references `lead-to-cash` for the conversion/credit-check detail rather than restating it, reworded the "Invoice handoff" step to reference `lead-to-cash`'s invoice description instead of duplicating its wording, and trimmed the matching `automatedActions` bullets the same way. `lead-to-cash` — the P0 flagship, full-funnel workflow — keeps its original full detail; `order-to-fulfilment` keeps its two genuinely unique steps (readiness governance, warehouse visibility) untouched.
**Reason selected:** Matches the plan's stated approach: "trim the more duplicated page's overlapping steps to a shorter cross-reference + link, keeping the fuller detail on the page that owns that part of the process — not deleting detail, relocating ownership." No information was removed from the site; a reader following `order-to-fulfilment` who wants the conversion/credit-check detail is pointed to `lead-to-cash`, which still has it in full.
**Structural fix:** Added `workflow-content.test.mjs`'s "no two routed workflows repeat the same sequence-step detail text verbatim" test — an exact-match guard (not fuzzy) that would have caught the original duplication and now prevents a future edit from silently reintroducing it, matching this project's established pattern of turning a found bug into a permanent test (see Phase 5 decision-log item 6, the analytics-events-sync fix).
**Risk:** The guard is exact-match only, so near-duplicate-but-not-identical phrasing could still slip through; judged acceptable since the original bug was verbatim duplication, not close paraphrase, and an exact-match test has no false-positive risk against legitimately similar-but-distinct steps elsewhere in the content.

## 7. Entity-naming collision: `/solutions/workflow-automation` and `/product/automation` shared the exact title "Workflow Automation"

**Finding:** While building `entity-architecture.md`'s canonical-name table, found `LANDING_SOLUTIONS`'s `workflow-automation` entry and `PLATFORM_PAGES`'s `/product/automation` entry both used the literal string "Workflow Automation" as their display `name`/`title` — two different pages, two different intents (a platform capability explainer vs. a buyer-problem-framed solution page that explicitly links to the platform page as its "go deeper" pairing), rendering with an identical page title, breadcrumb label, and analytics page-name.
**Decision:** Renamed the solution's `name` to "Automate Governed Workflows" — distinct, still accurately describes the page, and requires no slug/route/screenshot/freshness-key change since only the display name moved.
**Reason selected:** An identical title across two indexable pages is a real GEO/entity-clarity risk (which page is "the" Workflow Automation page, to a crawler or an answer engine) and a minor but real UX confusion risk (breadcrumbs/analytics both reading "Workflow Automation" for two different pages) — cheap to fix immediately rather than deferring to a later review cycle.
**Risk:** None identified — verified via `node --test packages/landing-content/tests/*.test.mjs` (101/101 pass) that no test asserted on the old name string.

## 8. Cycle 1 visual review: glossary index links had no persistent visual affordance

**Finding:** On `/resources/glossary`, every term (all 27, whether standalone or index-only) is a real, resolvable link — but the `<Link>` styling only added a color change and underline `on hover`, meaning at rest a glossary term looked visually identical to plain, non-interactive text. A screenshot at desktop width confirmed no linked term was visually distinguishable from the surrounding body copy without hovering each one individually — a real discoverability gap, not just a cosmetic nicety.
**Decision:** Added a persistent, subtle underline (`underline decoration-(--color-border-strong)`) to every glossary index link, switching to the brand color and a brand-colored underline on hover — so links are recognizable as interactive at rest, and still get a clear hover state.
**Reason selected:** A page whose entire purpose is "click through to learn more" failing to visually signal that its content is clickable is a real usability defect, caught by actually looking at a rendered screenshot rather than trusting the code — exactly the kind of finding Cycle 1 self-review exists to catch before it reaches Cycle 2's specialist agents.
**Risk:** None — re-verified via a fresh production build and a real screenshot that the fix renders correctly; `pnpm --filter @vercentlabs/landing typecheck`/`lint` stayed clean.

## 10. Cycle 2 fixes: a real regression from item 9's own fix, plus 8 further findings across 4 specialist agents

**Finding A (seo-aeo-geo-reviewer) — real regression, most severe**: item 9's fix (populating `erp-buying-guide`'s `relatedModuleKeys`) had a side effect nobody caught until a fresh agent tested the live rendered site: `app/modules/[slug]/page.tsx`'s backlink selection was plain `.slice(0, 1)` on array order, and `erp-buying-guide` (now 5 modules) sorts before the more specific `manufacturing-erp-guide` (2 modules) and `erp-vs-spreadsheets` (3 modules) in `RESOURCE_GUIDES`. Live-fetched confirmation: `/modules/manufacturing`, `/modules/stock`, and `/modules/procurement` all silently started linking to the generic buying guide instead of their topically-specific guide — `manufacturing-erp-guide` dropped to zero inbound module links, directly contradicting what `internal-link-graph.md` documented.
**Decision:** Changed the selection to sort candidates by specificity (fewest `relatedModuleKeys` first) before taking the first match — a general, principled rule, not a per-module hardcoded override. Added a new E2E regression test (`phase6-routes.spec.ts`, "module page resource-guide backlink specificity") asserting the actual selected guide per module, not just "a real guide exists," per the reviewer's own suggestion.
**Reason selected:** This is exactly the class of bug a content-layer unit test can't catch (it checks the data resolves, not which one a `.slice(0,1)` picks) — only a live-rendered check catches it, which is the entire reason Cycle 2 exists.

**Finding B (seo-aeo-geo-reviewer)**: `/resources/erp-requirements-checklist` rendered real FAQs but emitted no `FAQPage` JSON-LD (only `TechArticle`), unlike every sibling resource-guide route. **Fixed**: added the same `faqPageJsonLd` block used elsewhere.

**Finding D (seo-aeo-geo-reviewer)**: `/resources/feed.xml` was real and accurate but fully undiscoverable — no `<link rel="alternate">` anywhere, no visible on-page link. **Fixed**: added `alternates.types` to `ROOT_METADATA` (site-wide `<link>`) and a visible "RSS feed" link on `/resources`.

**Finding E (seo-aeo-geo-reviewer)**: the glossary index's `ItemList` JSON-LD listed `name` per term but no `item`/`url`, reducing machine-resolvability. **Fixed**: added `item: absoluteUrl(href)` for every entry that resolves to a real route.

**Finding F (seo-aeo-geo-reviewer)**: `entity-architecture.md` stated "4 industries" as simply canonical with no cross-reference to `information-architecture.md`, which — still marked "Decided" — specifies exactly 3. This is a real, already-made Phase 5 decision (not a Phase 6 error), but the two docs disagree with no link between them. **Fixed**: added an explicit footnote in `entity-architecture.md` cross-referencing the Phase 5 decision-log entry and naming the unreconciled inconsistency plainly rather than silently normalizing "4" as uncontested fact.

**Finding G (ux-cro-reviewer)**: `/resources`, `/resources/glossary`, and `/compare` — the 3 index/hub pages — had zero mid-page or final CTA blocks (only the site-wide header/footer/sticky-mobile CTAs), violating `conversion-architecture.md`'s "a final full-width CTA block before the footer on every page" requirement. Every one-level-deeper detail page correctly had both. **Fixed**: added the same `ContextualCta` + final inverse-tone CTA section already used on detail pages to all 3 index pages.

**Finding H (ux-cro-reviewer)**: the requirements checklist's "Print this checklist" button had no actual print stylesheet — `globals.css` had zero `@media print` rules, so printing would include the full header/footer/nav alongside the checklist, not the clean, standalone checklist the feature promises (confirmed via Playwright `page.emulateMedia({ media: 'print' })`). **Fixed**: added a global `@media print` rule hiding `header`, `footer`, and the sticky mobile CTA (added a `data-sticky-mobile-cta` attribute to make it targetable) — page-specific content stays controlled via the existing `print:hidden` Tailwind utility already used on the checklist's own filter bar.

**Finding I (ux-cro-reviewer)**: the requirements checklist's progress counter, "X of 73 marked," is ambiguous about whether it's counting individual requirements or capability groups. **Fixed**: reworded to "X of 73 groups reviewed."

**Finding J (ux-cro-reviewer, pre-existing, recorded not fixed)**: `/book-demo`'s success flow is a full-page redirect to `/book-demo/thank-you`, not an in-page success state — `conversion-architecture.md` specifies the in-page state as the default experience. This is Phase 3 architecture, out of Phase 6's scope to rebuild; recorded here for a future phase, matching the same record-only treatment given to the pre-existing `apps/web` bugs in item 6.

**Finding K (brand-design-reviewer)**: `/resources/[slug]`'s prose-guide body paragraphs had no `max-w` constraint, producing line lengths well past 100 characters at desktop widths — inconsistent with every other long-form template on the site (`ArticleHeader`'s dek, `FaqAccordion` answers, the glossary standalone template) which all correctly cap at `70ch`/`820px`. **Fixed**: added `max-w-[70ch]` to the guide body's wrapping `Stack`.

**Finding L (frontend-quality-reviewer)**: the requirements checklist's filter buttons distinguished the active filter by color alone, with no `aria-pressed`, leaving screen-reader users with no programmatic way to know which filter is selected. **Fixed**: added `aria-pressed={activeFilter === key}` to both button variants.

**Finding M (frontend-quality-reviewer)**: the root `package.json`'s `start` script (`node server.js`) requires the standalone server, but nothing in the automated `build`/`start` path ran `prepare-standalone.mjs` first — meaning a real deploy running "install → build → start" with no manual intervention would boot a 200-but-fully-unstyled-and-non-interactive site (confirmed reproducible by the reviewer after a clean build). Pre-existing (not introduced by Phase 6), but flagged as the single highest-stakes finding across all 6 reviews. **Fixed**: `apps/landing/package.json`'s own `build` script now always finishes with `node scripts/prepare-standalone.mjs`, so any caller of `pnpm build:landing` — including this project's real deploy path — gets a complete, servable standalone output automatically, matching what `infrastructure/docker/Dockerfile.landing`'s explicit copy steps already do.

**Multiple agents independently hit a transient broken-CSS/500 state mid-review**: traced to a stale standalone server process serving from an incomplete `.next/standalone` copy, made worse by concurrent agents each running their own diagnostic `next build` against the same shared directory (one agent's own build collided with the running server's file lock, per their own self-reported process note). Resolved by a clean stop → build → `prepare-standalone.mjs` → restart cycle; confirmed via a real screenshot that pages render fully styled afterward. Not a Phase 6 code defect — an artifact of running 6 review agents concurrently against one shared local server, made structurally less likely to recur in real deploys by Finding M's fix.

**Risk**: All fixes re-verified via `pnpm --filter @vercentlabs/landing typecheck`/`lint` (clean) after every change; full re-verification via rebuild + E2E suite is Cycle 3's job, not yet done as of this entry.
