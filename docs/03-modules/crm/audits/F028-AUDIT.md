Verified against `SUBREQUIREMENT_REGISTER.csv` (37 rows) by reading the `custom-field-definitions` resource schema (`index.js:1149-1168`) and searching for formula/expression evaluation and field-level role visibility.

**Correction (found 2026-09-05, while wiring F006's `qualification-criteria` resource and tracing how a generic resource actually becomes reachable):** `custom-field-definitions` and `custom-records` are registered in `apps/web/src/modules/crm/index.ts`'s `crmDefinitions` map (with a real, working admin form) but are **not present in `CRM_UI_RESOURCE_KEYS`/`CRM_API_RESOURCE_KEYS` (`scope.ts`) and have zero references anywhere in `apps/web/src/app`** — no page, no settings link, nothing. `/crm/custom-field-definitions` 404s (`isCrmUiResource` fails) and `GET/POST /api/crm/custom-field-definitions` 404s too (`isCrmApiResource` fails). This does not affect the domain-layer correctness of F028's fixes below — `createCrmRecord`/`updateCrmRecord` for these resources work correctly and are proven by real tests calling them directly — but no admin can reach the feature through the browser today. UX-001/002/003 and CAP-003 below are graded against what the domain layer does, not against browser-reachability, since that wasn't checked at the time; this note corrects that gap. Fixing this (the same `scope.ts` + settings-page wiring F006 just did for `qualification-criteria`) is a real, cheap follow-up, not done here since it's outside F028's own scope-of-record.
