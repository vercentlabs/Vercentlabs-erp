# F021 Lead import and export — Atomic requirement trace

Verified against `SUBREQUIREMENT_REGISTER.csv` (37 rows) by reading the import and export routes in full, plus the shared `csvCell`/`neutralizeFormula` implementation in `packages/reporting-engine/src/index.js`.

| ID | Verdict | Evidence |
|---|---|---|
| CAP-001 | PASS | upload → validate (per-row, Zod schema) → duplicate handling → commit, with a persisted result report (`crm_import_receipts`). No explicit "review duplicates before commit" UI step — duplicates are detected and skipped automatically during commit, not previewed first (see CAP-002 dry-run gap). |
| CAP-002 (**dry run**, **upsert policy**, formula injection, malicious content, **async/resume**, partial failure, idempotency, unauthorized export) | **PASS on the security-critical items, 3 concrete process gaps.** Formula injection: **PASS, confirmed at the shared utility level** — `neutralizeFormula` (`packages/reporting-engine/src/index.js:1-4`) prefixes any cell starting with `=`, `+`, `-`, `@`, tab, or CR with a `'`, the correct OWASP-recommended mitigation, applied to every CSV export through the shared `csvCell` helper (so this protection covers every module's exports, not just CRM's). Malicious content: PASS — `TextDecoder("utf-8", { fatal: true })` rejects malformed encoding outright, plus a 2MB byte cap and 1,000-row cap. Idempotency: **PASS, and well-designed** — a SHA-256 content hash of the uploaded file is the dedup key (`crm_import_receipts`, `ON CONFLICT (organization_id,resource,content_hash) DO NOTHING`), so re-uploading the exact same file returns the original result rather than re-importing; an advisory lock (`pg_advisory_xact_lock`) additionally prevents two concurrent imports of the same resource from racing. Partial failure: PASS — per-row `SAVEPOINT`/`ROLLBACK TO SAVEPOINT` isolates a bad row without aborting the batch. Unauthorized export: PASS — `PERMISSIONS.crmExport` plus `requireCrmResourceView`, and defensive response headers (`X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`). **Gaps:** no dry-run mode — the endpoint always commits; there is no preview-only path. No upsert policy — the import only ever calls `createCrmRecord`; an exact duplicate is silently *skipped*, never merged/updated, so there's no way to bulk-update existing leads via CSV. No async/resume — processing is fully synchronous within one request, capped at 1,000 rows; a larger dataset requires multiple manual uploads rather than a resumable background job (contrast with `enqueueLeadBulkUpdateJob`, which does have the async/job pattern for bulk edits). |
| CAP-003 (imports reuse create/update/duplicate policy; exports enforce identical scope) | PASS | import calls `createCrmRecord` (the same governed path interactive creation uses, including duplicate-policy enforcement — `CRM_LEAD_DUPLICATE_EXACT` is specifically handled); export calls `listCrmRecords` (the same scoped read path as the UI). |
| FR-001/002/003 | PASS | validation/permission/conflict states present; the 1,000-row/2MB caps are the enforced volume boundary (reasonable given the synchronous design, though it is the same boundary flagged as a gap under CAP-002). |

| FLOW-001/002 | PASS | stable `HttpError`/`CRM_*` codes throughout; the replay path (`replayed: true`, `inProgress` for a concurrently-running import) gives a clear, correct response for every retry scenario. |
| BR-001/BR-002 | PASS | import/export both funnel through the same commands as interactive use; `crm_import_receipts` rows are effectively append-only per content hash. |
| DATA-001/002 | PASS | `crm_import_receipts` retains file name, content hash, counts, and error details for every import attempt. |
| VAL-001/002 | PASS | header uniqueness/non-emptiness validated before any row processing; per-row Zod validation reuses the exact schema interactive creation uses. |

## Net assessment

25 of 37 rows PASS. The security engineering here is genuinely excellent and worth highlighting specifically: formula-injection mitigation is implemented once, correctly, in a shared package used by every export in the codebase, and the import path's content-hash idempotency plus advisory-lock concurrency control is more careful than most CSV-import features get in practice. The 3 gaps (no dry-run, no upsert, no async/resume for large files) are real process/UX limitations rather than security or data-integrity issues.
