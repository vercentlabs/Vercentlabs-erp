# F031 Customer master — Atomic requirement trace

Verified against `SUBREQUIREMENT_REGISTER.csv` (37 rows) by reading `services/api/src/modules/sales/index.js` in full (2,800+ lines), its option/report/dashboard read paths, the `getSalesOptions`/`getSalesReport` API routes, `database/tenant/migrations/008_sales_module.sql` and `database/tenant/migrations/001_business_data_foundation.sql` (the shared `business_parties`/`contacts`/`addresses` tables Sales consumes).

Sales does not own a "customer" entity of its own — F031's actual scope, per `F031-CAP-003` and `F031-SEM-06`, is that Sales correctly *consumes* CRM's shared `tenant.business_parties` (party_type IN customer/prospect/both) read-only, never duplicating or mutating that ownership. That framing drove this trace.

| ID | Verdict | Evidence |
|---|---|---|
| CAP-001/FR-001/US-001 | PASS | `getSalesOptions` surfaces the customer picker (search-by-typing is client-side over the returned set); quotations/orders reference `party_id`/`contact_id` throughout create/amend/read; `redactMargin`-gated detail reads and `getSalesReport`'s `customer-performance` report cover review/governance. |
| CAP-003/SEM-06 (module boundary, downstream consumption contract) | PASS | Confirmed via full-file grep: zero `INSERT`/`UPDATE`/`DELETE` against `tenant.business_parties`, `tenant.contacts` or `tenant.addresses` anywhere in the Sales module — every one of the ~6 read sites (`getSalesOptions`, the quotation/order party lookups, `getSalesReport`'s `customer-performance`) is a plain `SELECT`. Sales never transfers CRM's private-state ownership into itself, as the dossier's non-goal requires. |
| **SEC-001** (organization/company/branch scope enforced server-side) | **FAIL, found and fixed 2026-09-06 (live cross-company data leak).** `getSalesOptions` and all 9 variants of `getSalesReport` filtered only by `organization_id`, with zero `company_id` scoping, even though `business_parties`/`items`/`warehouses`/`crm_opportunities`/`sales_quotations`/`sales_orders` all carry a `company_id` column and RLS in this system is organization-only (verified in `001_business_data_foundation.sql`'s generic RLS-application block — there is no company/branch-level RLS anywhere; that scoping is an application-layer responsibility per query). A user restricted to one company could see every other company's customers, contacts, addresses, items, warehouses, CRM opportunities, quotations, orders and margin data through these two functions, while the sibling `getSalesDashboard` in the same file was already correctly scoped (`AND company_id=$2`). Fixed by mirroring that exact convention (and CRM's own `companyVisible()` predicate) across both functions: `allowAllCompanies` bypasses the filter; otherwise a row is visible only if `company_id IS NULL` (shared) or matches `activeCompanyId`; with no active company at all, nothing company-scoped is returned (fail closed). `contacts`/`addresses` don't carry their own `company_id`, so they're scoped via a join to their parent `business_parties.company_id`. Regression-tested in `services/api/tests/sales-options-company-scope-f031.test.mjs` (8 cases: scoped, `allowAllCompanies`, and fail-closed for both functions, plus the SEC-002 cost-redaction cases below). |
| **SEC-002** (cost/margin field-level restriction) | **FAIL, found and fixed 2026-09-06 (permission-gate bypass).** `standard_cost` is treated as sensitive everywhere else in the module — `redactMargin` strips it from quotation/order reads unless the caller has `sales.margin.view`, and `getSalesReport`'s `margin` key requires that permission outright — but `getSalesOptions`'s `items` query returned `standard_cost` unconditionally to any caller with only `sales.view`, the exact permission a front-line rep holds. The item picker used while building a new quotation/order was the one path that bypassed the module's own cost-protection convention. Fixed by passing `getSalesOptions`'s entire return value through the existing `redactMargin` helper (it recursively strips protected keys wherever they appear, so this affects only the `items` rows) rather than inventing a second redaction mechanism. Confirmed the web app does not currently read `standard_cost`/`standardCost` from options at all, so this was a pure unused leak with no UI to update. |
| DATA-001/002, BR-002 (snapshot/lineage) | PASS | `sales_quotation_versions`/`sales_order_versions` persist a `customer_snapshot` (plus contact/address/payment-term snapshots) at version-creation time (`:2378` area), so a later change to the customer master cannot retroactively alter an accepted quotation or confirmed order's historical customer data — the same snapshot-immutability pattern used for pricing/margin. |
| VAL-001 | PASS | `calculateLine` re-validates the referenced item belongs to the order's company (`item.company_id !== master.companyId` throws `409`) before any line is priced — the same company-scope discipline the SEC-001 fix now applies to the read side. |
| FR-003 / PERF-001 (enterprise volume, unbounded-query protection) | **GAP, recorded, not fixed this pass.** `getSalesOptions`'s `parties` query (the customer picker) has no `LIMIT`, unlike the `opportunities` query in the same function (`LIMIT 200`). An organization with a large customer base loads its entire active customer list into the picker on every quotation/order create. Scoped as a standing performance gap for the Sales gap-closing pass, not a security issue — no cross-tenant or cross-company data is involved, only volume. |
| SEC (redaction consistency, general) | PASS (by test evidence) | `redactMargin`'s recursive strip means any future field added to `protectedKeys` is enforced everywhere the helper is used, including the two return paths just fixed. |
| AUTO-001 / APP-001 / NOTIF-001 / REP-001 / AI-001 / INT-001 / INT-002 / UX-001-003 / CALC-001 / API-001/002 (beyond SEC-001) / OBS-001 / E2E-001-002 / UAT-001-002 | NOT INDEPENDENTLY VERIFIED | Not traced this pass; F031's scope was narrowed to the customer-consumption boundary and its read-path security, where the two real gaps above were found. |

## Net assessment (2026-09-06)

Two real, live, exploitable security gaps were found and fixed on first read of this feature — both cross-cutting (they affect every Sales screen that lists customers, contacts, addresses, items, warehouses, CRM opportunities, quotations, orders or margin data), so both were fixed immediately per the tracker's own methodology rather than deferred to a later pass. One scale/pagination gap was found and recorded for the Sales gap-closing pass. The module-boundary requirement this feature is actually about (Sales never owning or mutating CRM's customer data) held up cleanly under direct evidence.
