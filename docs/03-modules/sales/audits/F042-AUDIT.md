**Correction/context found after writing the above:** `scripts/validation/module-boundary-debt.json` already lists this exact line (`sales` module, `services/api/src/modules/sales/index.js`, `UPDATE tenant.crm_opportunities`) as pre-existing, grandfathered "legacy cross-module DML present at the platform freeze" — the architecture-verification gate (`verify-architecture.mjs`, run clean earlier this session) allows this specific entry but rejects any *new* boundary debt. So this isn't an undiscovered bug; it's a known, already-tracked debt item the team explicitly deferred ("module feature work must remove these entries over time"), not something introduced silently. The stage-history-completeness consequence described above is still real and still worth fixing, but the framing is "pay down known debt," not "newly found violation."

**Fixed in the Sales gap-closing pass (2026-09-06):** `confirmSalesOrder`'s raw `UPDATE tenant.crm_opportunities` is gone — it now only reports `sourceOpportunityId` in its return value. A new orchestration function, `confirmSalesOrderWithCrmSync` (`services/api/src/orchestration/sales-crm-opportunity-sync.js`), wraps it: after a successful confirmation, if the order has a source opportunity, it resolves the pipeline's `is_won` stage and a seeded `won`-type reason (falling back to the org-wide `WON_OTHER` reason every organization gets seeded with, per migration `056_crm_f001_f030_outcome_reasons.sql`) and calls CRM's own `moveOpportunityStage` — producing a real, complete `crm_opportunity_stage_history` row exactly like every other opportunity-close path. A CRM-side misconfiguration (no won stage or no won reason configured) is caught and swallowed so it can never block the Sales order action itself — order confirmation always succeeds or fails on its own merits.

The compensating reversal gap is also closed: a new `cancelSalesOrderWithCrmSync` reopens the opportunity into the pipeline's first non-terminal (`is_won=false AND is_lost=false`) stage if — and only if — the opportunity is still `won` at cancellation time (an opportunity someone already manually changed is left alone). Both wrappers are now what the order-actions route calls instead of the raw functions.

The `sales` → `crm_opportunities` entry was also removed from `scripts/validation/module-boundary-debt.json` (`verify-platform-foundation` re-run clean) — this pays down the tracked debt rather than leaving it recorded alongside a fix, since the actual violation is gone.

## Net assessment (2026-09-06)

The confirmation/credit/hold/cancel state machine and the readiness-governance engine are both excellent — the advisory-lock credit-exposure check in particular is a subtle concurrency correctness detail many systems miss. The cross-module boundary violation (order confirmation directly mutating CRM's `crm_opportunities` table instead of calling `moveOpportunityStage`) and its missing reversal path are both fixed — see above. No open gap remains from this audit.
