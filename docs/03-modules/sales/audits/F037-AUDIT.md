# F037 Quotation versions and revisions — Atomic requirement trace

Verified against `SUBREQUIREMENT_REGISTER.csv` (37 rows) by reading `insertQuotationVersion` in full (`services/api/src/modules/sales/index.js:~610-700`, the shared version-creation function `createQuotation` and `reviseQuotation` both call) and the `sales_quotation_versions` schema (`database/tenant/migrations/008_sales_module.sql:108-159`). This feature is really the versioning mechanics underneath F036, so most of the hard evidence overlaps with F036's `reviseQuotation` trace.

| ID | Verdict | Evidence |
|---|---|---|
| FLOW-001 (CURRENT -> SUPERSEDED, immutable versions) | PASS | Every revision inserts a brand-new `sales_quotation_versions` row with an incremented `version_number`; `sales_quotation_lines.quotation_version_id` FKs to that specific version, so a prior version's lines are structurally untouched by a later revision — immutability by construction, not by convention. `sales_quotations.current_version_id` is the only mutable pointer, atomically swapped to the new version on each revision. |
| CAP-002 (version numbering) | PASS | `versionNumber` is computed from a `next.rows[0].version` lookup scoped to the quotation before insert (sequential per-quotation, not a global counter). |
| CAP-002 (revision reason) | PASS, capture optional | `revision_reason` is a real column, populated from `input.revisionReason` on every revision — but `text()` allows `null`, so a revision can be saved with no reason. The dossier's omission gate asks the capability to *cover* revision reason, which it does (field exists, captured, displayed in `getQuotation`'s version history at `:970`); whether it should be *mandatory* is a judgment call, not a clear-cut gap — the module does enforce mandatory reasons elsewhere for lower-stakes actions (a single-line manual price override), which is worth reconsidering for consistency but isn't flagged as a hard defect. |
| CAP-002 (reapproval) | PASS | `reviseQuotation` unconditionally reverts `lifecycle_status` to `draft` regardless of the quotation's current status (approved, sent, etc. all revert) — reapproval through `submitQuotation` is structurally forced, not just recommended; there is no path to silently apply a revision to an already-approved/sent quotation without re-entering the approval gate. |
| CAP-002 (accepted-version binding) | PASS | `convertQuotationToOrder` (verified for F036) reads from `getQuotation`'s *current* version at conversion time, and `recordPublicQuoteDecision`'s accept path (not fully re-traced here, already noted present at F036) is bound to the specific `quotation_version_id` the customer was shown via their token — an accepted quotation is bound to the version that was actually presented, not whatever the latest version happens to be. |
| DATA-002 (tamper-evident snapshot) | PASS, stronger than the dossier requires | Each version stores a `content_hash = sha256(stable({input, preview: {lines, charges, totals}}))` (`:657-666`) — a deterministic content hash of the exact commercial terms at that version, beyond the dossier's baseline "immutable snapshot" ask; useful for detecting any out-of-band tampering with historical version rows. |
| BR-001 (single authoritative path) | PASS | Both `createQuotation` and `reviseQuotation` funnel through the same `insertQuotationVersion`, so no divergent version-creation logic exists between initial creation and later revision. |
| SEC-001/VAL-001 | PASS | `insertQuotationVersion` receives its `preview` from `previewSalesDocument`, which is the same company/party/UOM/currency/pricing-validated pipeline already verified for F031-F036 — no separate, less-validated path exists for revisions. |
| FR-003/PERF-001 | Same class already recorded (version-history read at `:970` has no explicit `LIMIT`, but per-quotation version counts are naturally small — lower urgency than the picker/list findings, not adding a new gap-closing line item for this alone). |

## Net assessment (2026-09-06)

No new gap beyond the minor, debatable "should revision reason be mandatory" observation. The versioning mechanics are structurally sound — immutability is enforced by the data model itself (new rows, not in-place updates), not just by application discipline, and the content-hash mechanism exceeds the dossier's baseline snapshot requirement.
