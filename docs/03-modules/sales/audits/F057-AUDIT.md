# F057 Sales commissions — Atomic requirement trace

Verified against `SUBREQUIREMENT_REGISTER.csv` (37 rows) by reading `createSalesCommissionRule`/`accrueSalesCommission` in full (`services/api/src/modules/sales/pass1-operations.js:129-161`), the `sales_commission_entries` schema (`database/tenant/migrations/071_pass1_f015_f114_operational_gaps.sql:163-181`), and tracing every caller of `accrueSalesCommission` (only the manual `action: "accrue-commission"` route).

This is a more nuanced finding than the F052/F054/F055/F056 cluster — the calculation core is genuinely correct, unlike those complete dead-ends; the gaps are in triggering and lifecycle progression, not the math itself.

| ID | Verdict | Evidence |
|---|---|---|
| CAP-001 (calculate explainable accruals from governed plans) | PASS | `accrueSalesCommission` resolves the applicable rule with real precedence (an explicit `ruleId`, or the most specific active rule matching company + owner + validity window, owner-specific preferred over general via `ORDER BY owner_user_id NULLS LAST`), computes `basisAmount × ratePercent` off either `net_sales` (subtotal) or `gross_margin` (margin_amount) per the rule's own `basis`, and is idempotent by natural key (`ON CONFLICT (organization_id, sales_order_id, owner_user_id, rule_id) DO UPDATE`) — re-running accrual for the same order/owner/rule updates the same row rather than duplicating it. |
| CAP-002 (basis: revenue/margin) | PASS | Both `net_sales` and `gross_margin` bases are real, distinct, validated options (`Set(["net_sales","gross_margin"])`), not a single hardcoded basis. |
| CAP-001 (automatic triggering) — **fixed in the gap-closing pass** | PASS | `confirmSalesOrderWithCrmSync` (`services/api/src/orchestration/sales-crm-opportunity-sync.js`, already the wrapper the order-actions route calls for the F042 CRM-sync fix) now also calls `accrueSalesCommission` automatically on order confirmation, using an elevated internal context (mirrors `crmSyncContext`'s shape) since the confirming rep won't usually hold `sales.settings.manage`. Most orders have no applicable commission rule configured at all — a normal, expected outcome, not a failure — so this step is unconditionally best-effort, same as the CRM sync: a missing rule, missing owner, or any other commission-configuration issue never blocks order confirmation. The schema was built for the full lifecycle; only the first step is wired. |
| CAP-002 (returns/credits, clawbacks) | Consequence of the above | Since nothing ever reverses a paid commission, a returned/credited order has no mechanism to claw back commission already accrued on it — moot until the lifecycle exists, but worth noting as the natural next gap once accrual is automated. |

## Net assessment (2026-09-06)

The calculation engine is real and correct — this distinguished F057 from the preceding cluster of complete dead-ends. The triggering gap is now fixed: accrual runs automatically on order confirmation, best-effort. The lifecycle-completion gap (approval/payout/reversal states exist in the schema but nothing progresses past `accrued`, and nothing in HR & Payroll ever reads this table) remains open — genuinely larger work (a real payroll integration), deliberately deferred.
