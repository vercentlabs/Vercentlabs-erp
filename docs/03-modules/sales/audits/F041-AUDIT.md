# F041 Approval workflow — Atomic requirement trace

Verified against `SUBREQUIREMENT_REGISTER.csv` (37 rows) by reading `apps/web/src/app/api/approvals/[id]/route.ts` in full and re-verifying the 2026-09-05 fix (`assertSameOrigin`/`requirePermissionFromSession(session, command.permission)` now gates both `approve` and `reject`), plus grepping the worker for any job touching `approval_requests` (none exists). This is genuinely shared cross-module infrastructure — Sales' `submitQuotation`/`approveQuotation`/`rejectQuotationApproval` (verified for F036) are one consumer of it, alongside Accounting's budget/invoice/bill/payment/journal approvals. Findings here apply to every module that uses approvals, not just Sales.

| ID | Verdict | Evidence |
|---|---|---|
| CAP-001/FLOW-001 (maker-checker, immutable decisions) | PASS | `assertSeparationOfDuties({requestedBy, actorUserId})` blocks a requester from approving their own request — real segregation of duties, not just a UI hint. Every decision is additionally logged to a separate insert-only `approval_decisions` table (distinct from the mutable `approval_requests` row), so a decision's history can never be edited after the fact. |
| SEC-001 (entity-specific authorization) | PASS (fixed 2026-09-05) | `requirePermissionFromSession(session, command.permission)` runs before either `command.execute` (approve) or `command.reject` — this is the exact fix from the earlier cross-module authorization bug found while first reconnoitering Sales (previously only the approve branch checked the entity-specific permission; rejecting anything only required the generic `approvals.manage`). Re-verified holding for the `sales.quotation.approve` command specifically (`orchestration/approvals.ts:121-146`, checked for F036). |
| FLOW-002 (concurrency-safe decisions) | PASS | Optimistic concurrency via `approval_requests.version`: the read, the final `UPDATE ... WHERE status='pending' AND version=$6`, and the client-supplied `expectedVersion` all have to agree, inside one `FOR UPDATE`-locked transaction — a second decision attempt on a stale view gets a stable `409`, not a silent double-decision. |
| DATA-002/BR-002 (evidence, non-rewrite) | PASS | `command_payload` is captured verbatim at request time and re-validated (`command.validate`) at decision time — the command that actually executes is bound to what was originally requested, not whatever the entity looks like now. |
| NOTIF-001 (partial) | PASS (in-app only) | A `notifications` row (`type: 'approval_decided'`) is inserted for the original requester on every decision — real, but in-app only; no evidence of email/push delivery for approval decisions specifically (matches the standing cross-feature notification-delivery gap CRM's own trace already found). |
| AUDIT | PASS | A structured `audit()` call records actor, before/after status+version, and the command key for every decision, in addition to the dedicated `approval_decisions` table. |
| **CAP-002 (multi-stage rules) — GAP, recorded, not fixed this pass.** | FAIL | The schema and route model exactly one decision point per `approval_requests` row (`pending -> approved/rejected`, one `decided_by`). There is no sequential multi-approver chain (e.g., manager then director) anywhere in this infrastructure — a request that should escalate through two approval stages would need two independently-triggered `approval_requests` rows created by application logic that doesn't exist. |
| **CAP-002 (delegation) — GAP, recorded, not fixed this pass.** | FAIL | `assigned_to` is set once at request-creation time (or left `NULL` for "any qualified approver"); there is no endpoint anywhere to reassign a pending approval to a different approver. An assigned approver who is unavailable has no delegation path — the request simply waits. |
| **CAP-002 (escalation, stale approvals) — GAP, recorded, not fixed this pass.** | FAIL | Grepped the entire worker service for any job referencing `approval_requests`: none exists. A `pending` approval has no expiry, no auto-escalation after a timeout, and no scheduled reminder — it can sit indefinitely with no system-driven follow-up, only whatever a human happens to notice. |
| CAP-002 (resubmission) | PASS | Verified via F036: `rejectQuotationApproval` reverts the quotation to `draft`; calling `submitQuotation` again from `draft` creates a fresh `approval_requests` row — rejection doesn't dead-end the document, and revising an already-submitted quotation explicitly cancels the stale pending request first (`reviseQuotation`, verified F036/F037) rather than leaving it orphaned. |
| VAL-001/002 | PASS | Zod-validated request bodies (`approvalDecisionSchema`), stable `HttpError` codes throughout, no restricted data leaked in error paths verified in this route. |
| AUTO-001 / FR-003/PERF-001 / REP-001 / AI-001 / INT-001/002 / UX-001-003 / API-001/002 / OBS-001 / E2E-001-002 / UAT-001-002 | NOT INDEPENDENTLY VERIFIED | Not traced this pass. |

## Net assessment (2026-09-06)

Core maker-checker mechanics (segregation of duties, optimistic concurrency, immutable decision history, entity-specific authorization after the earlier fix) are solid and correctly shared across modules. Three real, dossier-named gaps found — no multi-stage chains, no delegation, no escalation/staleness handling — all in the shared approval infrastructure, so fixing any of them benefits every module that uses approvals, not just Sales. Recorded for the gap-closing pass rather than fixed here since none are live authorization/data-leak bugs.
