# F046 Stock reservation — Atomic requirement trace

**Correction (2026-09-06):** this audit originally claimed reservation was "a local illusion" with no real Stock effect. That was wrong for the *intended* path — a real orchestration layer exists (`services/api/src/orchestration/sales-stock-reservation.js`) that genuinely calls Stock's canonical `reserveStock`, which really does update `tenant.stock_balances.reserved_quantity` (confirmed by `services/api/tests/pass1-f015-f114-runtime.test.mjs`'s "Pass1 stock reservation... updates reserved balance once" test, asserting exactly one `UPDATE tenant.stock_balances SET reserved_quantity=reserved_quantity+...`). The research error was scoping the original grep to `modules/sales/` only and missing `orchestration/`.

**However, investigating this correction surfaced a real, more serious, live bug**, found while wiring an unrelated F034 fix: `reserveSalesOrderLines` (`order-governance.js`, the *local-only* mirror function the orchestration layer calls internally) was **also directly exposed** on `POST /api/sales/orders/operations` as a bare `reserve_lines` action — reachable with no Stock call at all, bypassing the orchestration layer entirely. A caller hitting that endpoint got a success response implying stock was reserved, when only the local counter moved. **Fixed as part of this pass** (see below) by removing that duplicate, unsafe route action; the correctly-integrated `pass1-operations` route (`action: "reserve-stock"`) is the only remaining reservation entry point, and the UI (`pass1-operations-workspace.tsx`) already only ever used that one — the dangerous action had no live UI caller, only latent API exposure.
