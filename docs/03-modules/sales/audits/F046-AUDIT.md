# F046 Stock reservation — Atomic requirement trace

Verified against `SUBREQUIREMENT_REGISTER.csv` (37 rows) by reading `reserveSalesOrderLines` in full (`services/api/src/modules/sales/order-governance.js:935-1050`, already read for F042) and confirming — via a full-module grep for any import from `modules/stock` (zero matches) and comparing against `tenant.stock_balances.reserved_quantity` (the real ledger `getStockAvailability` reads, verified for F045) — what this function actually touches.

| ID | Verdict | Evidence |
|---|---|---|
| CAP-001 (request reservation without overselling) | PARTIAL, but the core promise is false — see the finding below | `reserveSalesOrderLines` does real, careful bookkeeping: row-locked (`FOR UPDATE`) reads, validates `reservedQuantity` against `confirmed - fulfilled - cancelled` per line, updates `fulfillment_status` to `allocated`/`partially_allocated` based on whether every line's reservation covers its remaining confirmed quantity. As a piece of internal arithmetic, it's correct. |
| **CAP-001/CAP-003 (the actual reservation) — serious cross-module finding, recorded, not fixed this pass.** | FAIL | `reserveSalesOrderLines` only writes to `tenant.sales_order_line_progress.reserved_quantity` — a Sales-private column. It never touches `tenant.stock_balances.reserved_quantity`, the real, shared inventory-reservation ledger that Stock's own `getStockAvailability` (verified F045) and the canonical Stock posting path (`postStockMovement`, verified elsewhere this session via the Manufacturing/POS cross-module tests) actually read and update. Confirmed via a full grep: the Sales module has **zero imports from `modules/stock`** anywhere. This means a Sales order that believes it has "reserved" stock has not actually removed that quantity from what Stock, Manufacturing, Procurement or POS see as available — nothing prevents another sales order, a POS sale, or a stock transfer from consuming the exact same physical inventory a confirmed Sales order believes it has claimed. "Reservation" in Sales is local bookkeeping with no real teeth. |
| CAP-002 (races) | FAIL, consequence of the above | The row-locking inside `reserveSalesOrderLines` only prevents two *Sales* callers from racing each other on the same line — it provides zero protection against a race with any *other* module's stock movement, because they don't share a ledger. |
| CAP-002 (release) | **GAP, recorded.** | There is no function anywhere that decrements `sales_order_line_progress.reserved_quantity` back down (e.g., on order cancellation or a line-level reduction) — `cancelSalesOrder` (verified F042) never touches reservation state, and no "release reservation" endpoint exists. |

## Net assessment (2026-09-06)

Likely the most serious functional finding in the entire Sales trace so far: stock "reservation" in Sales is a self-contained illusion — real, careful arithmetic against a counter that has no relationship to the actual, shared stock ledger every other module (Stock, Manufacturing, POS, Procurement) reads and writes. This means confirmed Sales orders provide no real protection against overselling physical inventory. Recorded as a priority item for the Sales gap-closing pass rather than fixed immediately — wiring this correctly (calling into Stock's canonical reservation/allocation path, handling the release-on-cancel gap too) is a genuine feature build, not a small patch, and touches Stock's side of the contract as much as Sales'.
