# F040 Taxes — Atomic requirement trace

Verified against `SUBREQUIREMENT_REGISTER.csv` (37 rows) by re-reading `calculateLine`'s tax block in full (`services/api/src/modules/sales/index.js:400-462`, already read for F033) and cross-checking it against `tenant.sales_tax_groups`/`tenant.sales_tax_group_components` (`database/tenant/migrations/008_sales_module.sql:21-54`) and the `tax_group_id` column present on `sales_quotation_lines`/`sales_order_lines`.

| ID | Verdict | Evidence |
|---|---|---|
| CAP-001/FR-001 (deterministic, non-AI tax calc) | PASS | Tax is computed server-side from `tenant.tax_rates` (rate, effective dates) keyed by the item's `tax_category_id` — no AI or client-supplied tax value is ever accepted; `input.supplyType` (`exempt`/`non_gst`/`export`) is the only thing that can suppress tax, and it's an explicit documented supply classification, not a free-form override. |
| CAP-002 (place of supply) | PASS | `buyerState` is derived with an explicit fallback chain (`input.placeOfSupply \|\| shipping.row.state_code \|\| billing.row.state_code`), compared against `sales_settings.seller_state_code` to decide intrastate vs. interstate — a real place-of-supply determination, not a hardcoded assumption. |
| CAP-002 (inclusive/exclusive tax) | PASS | When `priceList.tax_inclusive` is true, `taxableAmount` is back-calculated (`netAmount × 100 / (100 + taxRate)`) so the displayed line total isn't double-taxed; otherwise tax is added on top of the net amount. Both paths round through the same currency-aware `roundMoney`. |
| CAP-002 (exemptions) | PASS | `supplyType IN ('exempt','non_gst','export')` skips tax computation entirely for that line — a real, named exemption path, not an accidental zero-rate. |
| CAP-002 (components) | PASS | GST is correctly split into CGST+SGST (intrastate) or IGST (interstate) with each component computed independently off the same `taxableAmount` and stored as separate `tax_lines` rows — genuine multi-component tax evidence, not a single blended rate. |
| CAP-002 (effective dates) | PASS | The rate lookup filters `(effective_from IS NULL OR effective_from<=current_date) AND (effective_to IS NULL OR effective_to>=current_date)` and orders by `effective_from DESC` — a superseded historical rate can't accidentally apply, and company-specific rates (`company_id=$3`) take precedence over organization-wide ones via `ORDER BY company_id NULLS LAST`. |
| CAP-002 (rounding) | PASS | Every tax amount rounds through `roundMoney(..., master.currency.decimal_places)` — currency-aware, not a hardcoded 2-decimal assumption. |
| CAP-002 (overrides) | PASS (by design, not a gap) | No manual tax-amount override path exists anywhere, unlike price (which has an explicit `sales.price.override` + reason path). This reads as intentional: tax is meant to be strictly law/configuration-determined, consistent with the dossier's own framing ("without AI guessing") and the module-wide principle (verified elsewhere) that AI/manual action must never override deterministic tax truth. |
| **CAP-002 (stale configuration) — real finding, needs an owner decision, not fixed this pass.** | Unresolved schema duplication | `tenant.sales_tax_groups`/`tenant.sales_tax_group_components` exist with their own `tax_type`/`rate`/`compound_on_previous`/`recoverable` model, and `tax_group_id` is a real column on both `sales_quotation_lines` and `sales_order_lines` — but `calculateLine` never queries either table; it computes CGST/SGST/IGST inline in JS off `tenant.tax_rates`/`tax_categories` instead, and `tax_group_id` is always written as `NULL`. This is the same shape of finding as CRM's F013 (an unused schema sitting alongside the real implementation) — needs an owner decision (drop the unused tax-group schema, or is it meant to be wired up for non-GST jurisdictions/compound taxes the current inline logic doesn't handle?) rather than a unilateral code change. |
| DATA-002 (snapshot) | PASS | `tax_trace` (jsonb) and each line's own `tax_amount` are persisted at document-version creation — a later tax-rate change can't retroactively alter a historical quotation/order's tax. |
