# F047 Partial fulfilment — Atomic requirement trace

Verified against `SUBREQUIREMENT_REGISTER.csv` (37 rows) by reading `createFulfillmentRequest`/`completeFulfillmentRequest` in full (`services/api/src/modules/sales/index.js:2034-2085, 2711-2820+`) and confirming, via a full-repo grep for `sales_fulfillment_requests` and for callers of `completeFulfillmentRequest`/`postStockMovement`, that nothing anywhere connects Sales fulfillment completion to a real Stock movement.

| ID | Verdict | Evidence |
|---|---|---|
| CAP-001 (track partial delivery accurately) | PASS, at the bookkeeping level | `completeFulfillmentRequest` is idempotent by request id (`if (request.status==='completed') return ...`), row-locks the line progress, validates `fulfilled_quantity` against `confirmed - cancelled - returned` (correctly excludes cancelled/returned from the ceiling, not just confirmed), and derives the order's overall `fulfillment_status` (`fulfilled`/`partially_fulfilled`/`not_started`) from a real aggregate over every line rather than a single flag. |
| **CAP-001/CAP-003 (the actual fulfilment) — same root cause as F046, recorded together, not fixed this pass.** | FAIL | Neither `createFulfillmentRequest` nor `completeFulfillmentRequest` ever calls Stock's canonical stock-movement path (`postStockMovement`, verified elsewhere this session via the Manufacturing/POS cross-module tests). Confirmed by tracing callers: `completeFulfillmentRequest` is only reachable from `apps/web/src/app/api/sales/orders/[id]/actions/route.ts`, and `postStockMovement` is only reachable from the unrelated `apps/web/src/app/api/stock/movements/route.ts` — nothing anywhere connects the two. "Fulfilling" a Sales order updates Sales' own bookkeeping only; it does not decrement real inventory. This is the same underlying architectural gap as F046 (no real Sales-to-Stock integration for the physical side of an order), just manifesting on the completion side instead of the reservation side. |
| CAP-002 (multiple deliveries) | PASS | The request/complete model naturally supports multiple partial fulfilment requests over time — `fulfilled_quantity` accumulates (`next = current + fulfilled`) rather than being overwritten, so several partial shipments against the same order are correctly summed. |
| CAP-002 (billing basis) | PASS | `createInvoiceRequest`'s `quantityBasis` (`'ordered'` or `'fulfilled'`) is a real, explicit choice threaded into `buildHandoffPayload`, so invoicing can be configured to bill only what's actually been delivered rather than always the full order — correctly reconciles billing against partial fulfilment instead of assuming full shipment. |
| CAP-002 (services) | PASS (reasonable, given F033's finding) | Nothing in the fulfilment path distinguishes `item_type='service'` lines from stock items, but since F033 already found the whole module treats all catalog items uniformly regardless of type, this isn't a new gap specific to fulfilment. |
| CAP-002 (over/under-delivery tolerance, remainder cancellation) | **GAP, recorded.** | `next > maximum` is a hard rejection with zero tolerance — there's no configurable allowance for a slightly-over or slightly-under delivery (common in bulk/commodity fulfilment), and no explicit "cancel the remainder" action for a line that will never be fully fulfilled (e.g., a permanently discontinued item) — only the whole-order `cancelSalesOrder`, which is itself blocked once any fulfilment has occurred (verified F042). |
| FLOW-002 (idempotent request creation) | PASS | `createFulfillmentRequest` requires a caller-supplied idempotency key and returns the existing request on replay — a retried request creation can't create a duplicate handoff. |

## Net assessment (2026-09-06)

The bookkeeping half of partial fulfilment (accumulation across multiple requests, correct ceilings, billing-basis flexibility) is solid. The physical half is missing entirely — same root cause as F046: nothing in Sales ever calls Stock's real stock-movement system, so "fulfilling" an order is pure local record-keeping with no actual inventory effect. Recommend these two findings be fixed together in the gap-closing pass since they're one integration gap (Sales-to-Stock) manifesting in two features, not two separate problems. One smaller gap also recorded: no delivery tolerance or remainder-cancellation action.
