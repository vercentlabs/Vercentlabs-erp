# Frontend Rebuild — Contract Register

`FRONTEND_CONTRACT_REGISTER.csv` is the pre-deletion inventory of what the
legacy `apps/web` frontend exposes, captured before `apps/web`,
`packages/shared-ui`, and `packages/ui-web` are deleted as part of the
clean-slate rebuild (see `docs/01-standards/TECH_STACK_ADR_002_FRONTEND_REWRITE.md`
for the stack decision this rebuild follows; note the primitive layer is
React Aria Components, not Base UI, per owner direction on 2026-09-14 —
this supersedes the Base UI choice recorded in that ADR).

## What this register is

One row per route file that existed in `apps/web/src/app` at extraction
time (2026-09-14): 141 `page.tsx` + 399 `route.ts` = 540 rows. Generated by
`extract-contract-register.mjs` (scratch script, not checked in) by walking
the route tree directly — there is no OpenAPI/swagger spec in this repo to
diff against, so the route tree itself is the ground truth for "what
currently exists."

Structural columns (`current_route`, `target_route`, `backend_endpoint`,
`http_method`, `module`, `notes`) are mechanically derived and accurate as
of extraction time. All other columns (`feature_id`, `requirement_id`,
`permission`, `domain_command`, `validation_behavior`,
`concurrency_behavior`, etc.) are marked `TBD` rather than guessed —
producing fabricated mappings here would be worse than no mapping, since it
would look authoritative without being verified.

## Where the real requirement detail lives

Do not try to duplicate `SUBREQUIREMENT_REGISTER.csv` (18,870 rows) or
`UX_TRACEABILITY_REGISTER.csv` (20,958 rows, currently an unpopulated
skeleton — every UI-specific column blank) into this file. Instead:

- **Requirement-level detail**: `docs/02-register/SUBREQUIREMENT_REGISTER.csv`
  (`requirement_id`, `feature_id`, `capability_id`, `normative_statement`,
  `acceptance_criteria_ids`, `test_ids`, `status`).
- **Feature-level implementation evidence**:
  `docs/03-modules/<module>/features/F###-AUDIT.md` files cited from
  `docs/PRODUCTION_TRACKER.md` — these have real file+line evidence of
  current behavior, which this CSV does not attempt to re-derive.
- **Capability grouping**: `docs/02-register/CAPABILITY_REGISTER.csv`.

As each module is rebuilt, its rows in this CSV should be updated in place:
fill in `feature_id`/`requirement_id`/`permission`/etc. from the sources
above as that route's replacement is actually built (not before), and flip
`migration_status` from `NOT_STARTED` through `FOUNDATION` /
`IMPLEMENTED` / `VERIFIED` to match `docs/ux/UI_REWRITE_TRACKER.md`'s
per-requirement classification discipline. This keeps the register honest:
a filled-in row means "this was actually checked against the new
implementation," not "this was guessed at deletion time."

## Known pre-existing duplication resolved by this rebuild

`current_route` values containing `leads-next` (the in-progress Base
UI/TanStack golden reference built under the now-superseded stack choice)
map to `target_route` = the equivalent canonical `/crm/leads*` path. That
in-progress work is being discarded, not migrated — see
`docs/ux/UI_REWRITE_TRACKER.md` history and the ADR note above for why.
